# Audit report

## [High] AssignmentHook pulls ERC20 prover fee from attacker-chosen meta.coinbase instead of the proposer

File: AssignmentHook.sol
Function: onBlockProposed()

When assignment.feeToken != 0 the hook executes IERC20(feeToken).safeTransferFrom(_meta.coinbase, _blk.assignedProver, proverFee). _meta.coinbase comes from params.coinbase in LibProposing.proposeBlock, which is a free parameter of the proposer (it only defaults to msg.sender when zero). Neither the hook nor LibProposing checks that coinbase == msg.sender, and the prover signature (hashAssignment) covers neither the coinbase nor the proposer. Any account that granted the AssignmentHook an allowance for the fee token (normal for proposers paying in ERC20) can therefore be charged by a third party. The same unbound signature can also be replayed by anyone for another block with the same blobHash before expiry.

Attack path: 1) Victim proposer V has approved AssignmentHook for token T. 2) Attacker controls prover address P, signs an assignment with feeToken=T and tierFees[minTier] = V's balance/allowance. 3) Attacker calls TaikoL1.proposeBlock with assignedProver=P, coinbase=V, hookCalls=[AssignmentHook]. 4) Hook pulls the liveness bond from P (returned later when P proves) and transfers proverFee of T from V to P.

Impact: Theft of any ERC20 balance that users approved to AssignmentHook, up to their allowance.

## [High] ERC20Airdrop2 users can only withdraw full allocation in the single second at window end

File: ERC20Airdrop2.sol
Function: withdraw() / getBalance()

getBalance unlocks linearly: timeBasedAllowance = balance * (min(now, claimEnd+withdrawalWindow) - claimEnd) / withdrawalWindow, so 100% is only unlocked at claimEnd+withdrawalWindow. The ongoingWithdrawals modifier, however, reverts whenever claimEnd + withdrawalWindow < block.timestamp. The unlock period and the withdrawal period are the same interval, so the full amount is withdrawable only in the block whose timestamp equals exactly claimEnd+withdrawalWindow. Any portion not withdrawn by then is locked forever.

Attack path: 1) User claims during claim period. 2) During the window the user withdraws partially (e.g. at 50% elapsed). 3) Window ends; remaining amount unlocks only at the last second and afterwards every withdraw() reverts with WITHDRAWALS_NOT_ONGOING.

Impact: Users permanently lose part of their claimed airdrop (in expectation almost always some fraction).

## [High] TimelockTokenPool withdraw signature has no nonce/contract/chain binding and can be replayed

File: TimelockTokenPool.sol
Function: withdraw(address,bytes)

The signed message is keccak256(abi.encodePacked("Withdraw unlocked Taiko token to: ", _to)) only. It contains no nonce, deadline, amount, contract address or chain id, and nothing marks a signature as used. Once a recipient publishes one signature, anyone can call withdraw(_to, sig) again at any later time and on every other TimelockTokenPool instance (investors, team, grantees) where the same recipient holds a grant. Each call moves all currently unlocked tokens to _to and pulls costToWithdraw of the cost token from the recipient via safeTransferFrom.

Attack path: 1) Recipient R signs once to withdraw to address X (e.g. a one-off or exchange deposit address). 2) Later, attacker replays (X, sig) on this pool and on other pools where R has grants. 3) Newly unlocked TKO is sent to X and R is charged the USD cost at times he did not choose.

Impact: Recipients lose control over their vested tokens (sent to a possibly no longer controlled address) and are forced to pay cost tokens; cross-pool replay.

## [High] TaikoL2 base fee: gas issuance counted repeatedly because lastSyncedBlock updates every 5 L1 blocks

File: TaikoL2.sol
Function: anchor() / _calc1559BaseFee()

_calc1559BaseFee issues numL1Blocks = _l1BlockId - lastSyncedBlock times gasTargetPerL1Block of gas on every L2 block and subtracts it from gasExcess. But anchor() only updates lastSyncedBlock when _l1BlockId > lastSyncedBlock + BLOCK_SYNC_THRESHOLD (5). For all L2 blocks in between, lastSyncedBlock stays stale, so the same L1 blocks are counted again and again (e.g. 1,2,3,4,5 L1 blocks of issuance in successive L2 blocks instead of 1 each). gasExcess is driven down far faster than intended.

Attack path: Happens in normal operation: each anchor between syncs recomputes issuance from the stale lastSyncedBlock; a busy chain still sees gasExcess collapse toward 1.

Impact: Base fee is systematically underpriced (pushed to the minimum), breaking EIP-1559 congestion pricing and enabling cheap L2 block-space spam / DoS.

## [Medium] Top-tier (guardian) re-proof always panics because contestBond is set to 1, not 0

File: LibProving.sol
Function: proveBlock()

For a same-tier proof on the top tier (contestBond == 0) the code asserts ts.validityBond == 0 && ts.contestBond == 0 && ts.contester == address(0). However every write path sets ts.contestBond = 1 as a gas-saving sentinel: _createTransition and _overrideWithHigherProof both write _ts.contestBond = 1. Therefore after the guardian has proven a transition once, any later guardian proof with a different blockHash/stateRoot reaches the assert and reverts with Panic. The documented ability of the top tier to re-prove/correct a transition before verification is dead code.

Attack path: 1) Guardians prove transition B for block N (e.g. by mistake or under a compromised quorum). 2) Guardians try to re-prove the correct transition A via GuardianProver.approve -> TaikoL1.proveBlock. 3) assert(ts.contestBond == 0) fails, the call reverts; after the cooldown B is verified.

Impact: A wrong top-tier proof can never be corrected; an incorrect state root can be finalized and synced to the SignalService (bridge funds rely on it).

## [Medium] Bridge watchdog can mark any unproven message as received via suspendMessages(false)

File: Bridge.sol
Function: suspendMessages() / processMessage() / recallMessage()

suspendMessages(hashes, false) writes proofReceipt[msgHash].receivedAt = block.timestamp for arbitrary hashes, including hashes that were never proven. processMessage and recallMessage treat receivedAt != 0 as isMessageProven and then skip _proveSignalReceived entirely. So the 'unsuspend' action turns a role that should only pause/ban into one that can inject arbitrary messages. After the invocation delay (+extra delay, since preferredExecutor is 0) anyone can execute the fabricated message.

Attack path: 1) bridge_watchdog calls suspendMessages([hash(fake msg to ERC20Vault minting/releasing tokens)], false). 2) After invocationDelay+extraDelay, call processMessage(fakeMsg, anyProof). 3) Vault releases canonical tokens or mints bridged tokens; similarly recallMessage can be used to recall a delivered message (double spend).

Impact: Full drain of vault-held assets by the watchdog role, which is supposed to have only suspension powers.

## [Medium] CrossChainOwned cannot execute onlyOwner functions: self-call makes msg.sender the contract

File: CrossChainOwned.sol
Function: onMessageInvocation()

onMessageInvocation checks ctx.from == owner() (an address on the owner chain) and then executes address(this).call(txdata). Inside the target function msg.sender is address(this), so every onlyOwner function (EssentialContract._authorizeUpgrade, _authorizePause, TaikoL2EIP1559Configurable.setConfigAndExcess, Ownable transferOwnership) reverts because owner() != address(this). Both conditions cannot hold simultaneously (owner would have to equal the contract itself and also be the L1 sender), so the call fails with XCO_TX_REVERTED.

Attack path: 1) L1 owner sends a bridge message to TaikoL2 with txdata = upgradeTo(...) or setConfigAndExcess(...). 2) Bridge invokes onMessageInvocation; ctx check passes. 3) address(this).call reverts on onlyOwner; message becomes RETRIABLE/FAILED.

Impact: TaikoL2 (and other CrossChainOwned contracts) cannot be upgraded, paused or reconfigured cross-chain; emergency response is impossible.

## [Medium] Relayer can force a message to fail by supplying less gas than message.gasLimit

File: Bridge.sol
Function: processMessage()

For a non-owner caller, gasLimit = _message.gasLimit is passed to excessivelySafeCall, but the Bridge never checks that gasleft() is at least gasLimit (plus overhead). By the 63/64 rule the callee receives less gas than the user paid for, runs out of gas, and the outer call continues: the message is set to RETRIABLE and the relayer still collects _message.fee.

Attack path: 1) Relayer calls processMessage with a gas amount just enough for the outer logic. 2) Inner call OOGs, status RETRIABLE. 3) Relayer receives fee; destOwner must retry and pay gas, or the action loses its time-sensitivity.

Impact: Relayers can collect fees without delivering, delaying or breaking time-sensitive messages (e.g. governance via CrossChainOwned, DeFi actions).

## [Medium] SGX instance expiry bypass: every proof resets validSince for the replacement key

File: SgxVerifier.sol
Function: verifyProof() / _replaceInstance()

INSTANCE_EXPIRY (180 days) is meant to force periodic re-attestation. However _replaceInstance writes instances[id] = Instance(newInstance, block.timestamp) on every successful proof, so the validity clock restarts each time. In addition newInstance is not checked against or recorded in addressRegistered. An instance attested once (even on an old, later-revoked TCB) can therefore keep proving forever by rotating keys.

Attack path: 1) Instance registers via registerInstance. 2) It submits a proof at least once every 180 days, each time naming a new key. 3) It never needs a fresh attestation even if its enclave/TCB is later considered insecure.

Impact: Defeats the expiry-based security model of the SGX tier; a compromised enclave stays trusted indefinitely unless manually deleted.

## [High] AssignmentHook charges ERC20 prover fee to proposer-chosen coinbase, draining approvals

File: AssignmentHook.sol
Function: onBlockProposed()

For ERC20 fees the hook executes IERC20(assignment.feeToken).safeTransferFrom(_meta.coinbase, _blk.assignedProver, proverFee). _meta.coinbase is params.coinbase, which the caller of TaikoL1.proposeBlock sets freely (LibProposing only defaults it to msg.sender when it is zero). The prover signature checked via hashAssignment covers feeToken, tierFees, expiry, blobHash and so on, but it does not bind the proposer or the coinbase, and the assignedProver and the tierFees are themselves chosen by the proposer. The party that pays the fee is therefore an arbitrary third party, not the caller. Every prover has to approve TKO to the AssignmentHook so that tko.transferFrom(assignedProver, taikoL1, livenessBond) works, and proposers approve their fee token to it as well, so standing allowances to the hook are normal.

Attack path: 1) Attacker picks a victim V that has a large allowance of token T to AssignmentHook (for example an honest prover with a TKO allowance, T = TKO). 2) Attacker uses an address A as assignedProver and signs an assignment with feeToken = T, a valid expiry and tierFees containing the block minTier (and the 0.1 percent higher tier) with fee = min(V allowance, V balance). 3) Attacker calls TaikoL1.proposeBlock with params.coinbase = V, assignedProver = A, a small txList and a hookCall to AssignmentHook with that assignment. 4) The hook pulls the 250 TKO liveness bond from A and then moves the fee from V to A. 5) Repeat until the allowance is used up.

Impact: Theft of any token allowance granted to the AssignmentHook (TKO or stablecoins), limited only by the 250 TKO liveness bond the attacker risks per block, which is partly or fully recoverable if A proves the block.

## [High] SGX registerInstance accepts any genuine enclave: MRENCLAVE/MRSIGNER check disabled by default

File: AutomataDcapV3Attestation.sol
Function: _verifyParsedQuote()

Step 2 of _verifyParsedQuote only compares localEnclaveReport.mrEnclave and mrSigner with _trustedUserMrEnclave and _trustedUserMrSigner when the private flag _checkLocalEnclaveReport is true. The flag defaults to false and toggleLocalReportCheck() only flips it. DeployOnL1.s.sol deploys AutomataDcapV3Attestation and SetDcapParams.s.sol calls setMrEnclave and setMrSigner, but nothing in the scripts calls toggleLocalReportCheck, so the allow-list is stored but never enforced. SgxVerifier.registerInstance has no access control and registers address(bytes20(localEnclaveReport.reportData)) after INSTANCE_VALIDITY_DELAY. The remaining checks (Intel cert chain, QE identity, TCB level) prove only that some genuine SGX machine produced the quote, not that it runs the Taiko prover program. The flag is also a toggle, not a setter, so a second call silently disables it again.

Attack path: 1) Attacker runs their own enclave on any SGX capable machine that writes a key they control into reportData. 2) Attacker calls SgxVerifier.registerInstance with the parsed quote; verification passes without checking the enclave measurement. 3) After one day the instance is valid. 4) Attacker signs SGX tier proofs (VERIFY_PROOF hash) for forged transitions with a chosen stateRoot and proves blocks at the SGX tier (the minimum tier for about 99.9 percent of blocks). 5) If nobody contests within the 24 hour cooldown, the forged state root is verified and synced to the SignalService, and forged signal proofs can drain the bridge.

Impact: Anyone can mint a trusted SGX prover identity and forge validity proofs, leading to false state roots and loss of bridged funds. Depends on the deployment never enabling the local report check; the code and scripts as shipped do not.

## [Medium] Guardian re-prove branch always panics: assert(contestBond == 0) but contestBond is kept at 1

File: LibProving.sol
Function: proveBlock()

In the else-branch for a proof on the same tier as the stored transition, the top tier path asserts assert(ts.validityBond == 0 && ts.contestBond == 0 && ts.contester == address(0)) before overwriting prover, blockHash and stateRoot. But _createTransition initialises ts_.contestBond = 1 ('to save gas') and _overrideWithHigherProof sets _ts.contestBond = 1 again, so a transition that sits at the guardian tier always has contestBond == 1. The assertion therefore fails (Panic 0x01) every time a guardian tries to replace an existing guardian-tier transition with a different blockHash or stateRoot. The documented behaviour 'the top tier prover re-proves' can never execute.

Attack path: 1) Guardians prove block B with transition T1 at TIER_GUARDIAN (wrongly, or after a bad minority decision, or to settle a contest). 2) The error is noticed and guardians approve T2 with the same parentHash via GuardianProver.approve. 3) proveBlock reaches the isTopTier re-prove branch and the assert fails, the whole call reverts, including the approval bits just written. 4) After the 60 minute guardian cooldown T1 is verified and its stateRoot is synced to the SignalService.

Impact: A wrong guardian-tier proof is irreversible; the last-resort safety mechanism cannot correct itself, and a wrong state root can become final and be used for bridge withdrawals.

## [Medium] CrossChainOwned self-call can never pass onlyOwner, so L1 governance cannot manage TaikoL2

File: CrossChainOwned.sol
Function: onMessageInvocation()

onMessageInvocation requires ctx.srcChainId == ownerChainId and ctx.from == owner(), where owner() is an address on the owner chain (the genesis config sets TaikoL2 owner to the L1 timelock controller). It then executes address(this).call(txdata). Inside that call msg.sender is the TaikoL2 proxy itself, so every function guarded by onlyOwner, onlyFromOwnerOrNamed or _authorizeUpgrade (upgradeTo, pause, unpause, transferOwnership, setConfigAndExcess, withdraw) compares msg.sender == address(this) with owner() and reverts with XCO_TX_REVERTED. The two conditions (caller must be the L1 owner, and the inner caller must be the same owner) can only both hold if the L1 owner address equals the L2 contract address.

Attack path: 1) The L1 owner sends a bridge message to TaikoL2 with data for upgradeTo, pause or setConfigAndExcess. 2) The Bridge calls onMessageInvocation, the checks pass. 3) The self-call hits onlyOwner and reverts; txId is not advanced and the message ends up retriable or failed. 4) No other path exists because the owner address is not an L2 account.

Impact: TaikoL2 (and TaikoL2EIP1559Configurable) cannot be upgraded, paused, reconfigured or have funds withdrawn through the intended cross-chain owner, so a bug on L2 cannot be fixed or paused by governance.

## [Medium] ERC20Airdrop2.withdraw reverts after the vesting window, forfeiting unwithdrawn tokens

File: ERC20Airdrop2.sol
Function: withdraw()

getBalance vests claimedAmount linearly over withdrawalWindow starting at claimEnd and the doc says it becomes fully withdrawable at the end of the window. But the ongoingWithdrawals modifier reverts with WITHDRAWALS_NOT_ONGOING when claimEnd + withdrawalWindow < block.timestamp. So once the window is over, withdraw can no longer be called and everything not yet withdrawn (which is the full remainder at the moment the allowance reaches 100 percent) can never be claimed. Because the allowance only reaches 100 percent at exactly the end of the window, a user who withdraws before that always leaves a remainder behind unless the transaction lands exactly in the last second.

Attack path: 1) User claims during the claim period. 2) User withdraws part of the balance during the window, or waits. 3) After claimEnd + withdrawalWindow every withdraw(user) call reverts. 4) The remaining claimedAmount minus withdrawnAmount stays in the vault forever.

Impact: Permanent loss of airdrop tokens for users who do not withdraw in the final second of the window; funds remain stuck with the vault.

## [Medium] TaikoL2 basefee re-applies L1 gas issuance since stale lastSyncedBlock for every L2 block

File: TaikoL2.sol
Function: _calc1559BaseFee()

numL1Blocks is computed as _l1BlockId - lastSyncedBlock, and issuance = numL1Blocks * gasTargetPerL1Block is subtracted from gasExcess at every anchor. lastSyncedBlock is only updated in anchor() when _l1BlockId > lastSyncedBlock + BLOCK_SYNC_THRESHOLD (5). Between syncs, every L2 block therefore subtracts the issuance for all L1 blocks since the last sync, not only the blocks since the previous anchor. With about four L2 blocks per L1 block and a sync period of six L1 blocks the issuance subtracted is roughly 1+2+...+6 times four, about 14 times the intended 6 L1 blocks of gas, while at most 15M gas per L2 block is added. The result is that excess = excess > issuance ? excess - issuance : 1 collapses to 1 quickly and basefee sits at the minimum.

Attack path: 1) Normal operation: anchors reference L1 heights l1Id with lastSyncedBlock lagging up to 5 blocks. 2) Each anchor subtracts (l1Id - lastSyncedBlock) * 60M gas from gasExcess. 3) gasExcess is driven to the floor of 1 and basefee_ = Lib1559Math.basefee(1, ...) is 0, forced to 1 wei. 4) An attacker fills L2 blocks with cheap transactions without the fee market reacting.

Impact: The dynamic L2 fee mechanism is largely disabled; blockspace is underpriced, enabling cheap spam and under-compensation of proposers/provers who pay L1 costs.

## [Medium] Bridge.processMessage zero-value refund to contract refundTo reverts, message can never finish

File: Bridge.sol
Function: processMessage()

After invoking the message, processMessage always executes either refundTo.sendEther(_message.fee + refundAmount) or msg.sender.sendEther(_message.fee) followed by refundTo.sendEther(refundAmount). In the normal success path refundAmount is 0 and fee is often 0, so a zero-value call with empty calldata is made. LibAddress.sendEther reverts with ETH_TRANSFER_FAILED if the call fails, and a contract without receive/fallback reverts on that call even with value 0. refundTo defaults to destOwner, which defaults to the sender contract in the vaults. A message whose refundTo/destOwner is such a contract can therefore never be processed (the revert undoes the status update) and, because recallMessage needs a failure signal that is only produced after a processed message becomes FAILED, it can never be recalled either.

Attack path: 1) A smart contract wallet without a payable receive/fallback calls ERC20Vault.sendToken (destOwner and refundTo default to it). 2) The tokens are locked in the source vault and the message is sent. 3) Any relayer or the owner calls processMessage; the final sendEther(0) to the contract reverts the whole call. 4) The message stays NEW forever, no failure signal can be produced, recallMessage fails with B_NOT_FAILED.

Impact: Permanent lock of the bridged assets for contract senders/owners lacking a receive function; relayers that are such contracts also cannot collect fees.

## [Medium] Vaults call sendEther(0) on recipients: contract receivers without receive() make transfers fail

File: ERC20Vault.sol
Function: onMessageInvocation()

ERC20Vault, ERC721Vault and ERC1155Vault finish onMessageInvocation with to.sendEther(msg.value), and onMessageRecalled with _message.srcOwner.sendEther(_message.value), unconditionally. LibAddress.sendEther reverts when the low level call fails, and a contract without a payable receive/fallback fails a call with empty data even when the value is 0. Token delivery to such a contract (many token-receiving contracts have no receive function) therefore always reverts after the tokens were already minted/transferred inside the same transaction, which rolls back, making the message RETRIABLE and then FAILED. On recall, if srcOwner is a contract without receive the recall always reverts, so the locked tokens cannot be returned.

Attack path: 1) User bridges tokens with _op.to (or srcOwner) set to a contract that has no receive/fallback. 2) On the destination, onMessageInvocation mints/transfers the tokens and then calls to.sendEther(0), which reverts. 3) The message fails; if srcOwner is the same kind of contract, onMessageRecalled reverts on srcOwner.sendEther(0) and the assets remain in the source vault.

Impact: Bridging to or from contracts without a receive function is impossible, and in the recall case the user loses access to the locked tokens.

## [Medium] ERC20Airdrop.claimAndDelegate can be blocked by front-running delegateBySig and burning the nonce

File: ERC20Airdrop.sol
Function: claimAndDelegate()

claimAndDelegate verifies the Merkle claim, transfers the tokens and then calls IVotes(token).delegateBySig(delegatee, nonce, expiry, v, r, s) with caller supplied delegationData, and it is the only claim path. The signature data sits in the public mempool. Anyone can call TaikoToken.delegateBySig directly with the same parameters first, which consumes the signer nonce; the user claim then reverts inside delegateBySig because the nonce is no longer valid, and the whole claim rolls back. The user needs a new signature and the attacker can repeat this for every retry until claimEnd. Also, any third party can claim for the user with their own valid delegation data, so the user does not get their intended delegation.

Attack path: 1) User submits claimAndDelegate(user, amount, proof, delegationData). 2) Attacker sees the pending tx and calls token.delegateBySig with the same (delegatee, nonce, expiry, v, r, s) with higher gas. 3) The attacker tx succeeds, the nonce is used, the user tx reverts. 4) Repeat on each new signature until the claim period ends.

Impact: Targeted denial of the airdrop claim for chosen users until the claim window closes.

## [Medium] Bridge.suspendMessages(false) marks never-proven message hashes as proven, skipping signal proof

File: Bridge.sol
Function: suspendMessages()

suspendMessages writes proofReceipt[msgHash].receivedAt = type(uint64).max when suspending and block.timestamp when unsuspending, for any hash, whether or not a proof was ever verified. processMessage and recallMessage both treat receivedAt != 0 as 'message already proven' and skip _proveSignalReceived (and in recallMessage also the isSignalSent and failure-signal checks). So suspending an unproven hash and later unsuspending it (or unsuspending directly) creates a proof receipt out of nothing. After invocationDelay (plus extra delay) anyone can execute a message that was never sent on the source chain, or recall one that never failed.

Attack path: 1) The owner or bridge_watchdog calls suspendMessages([h], false) for a crafted message hash h (also reachable by a watchdog that suspended a still unproven suspicious hash and later unsuspends it). 2) After the delay processMessage(message, emptyProof) passes the isMessageProven path and invokes the message, spending bridge Ether; or recallMessage pays out _message.value for a message that does not exist.

Impact: The watchdog role, which should only be able to delay messages, can authorise arbitrary messages and drain the bridge; accidental unsuspend of an unproven hash has the same effect.

## [Medium] Bridge.retryMessage ignores addressBanned, banned targets can still be invoked

File: Bridge.sol
Function: retryMessage()

processMessage skips the external call and refunds when addressBanned[_message.to] is set, but retryMessage calls _invokeMessageCall directly without checking addressBanned. A message that is already RETRIABLE when the watchdog bans its target can still be retried by anyone (when gasLimit != 0 and it is not the last attempt) or by the destOwner, and the call to the banned address with the full message.value is executed.

Attack path: 1) A message to a malicious contract M fails once (for example by out of gas) and becomes RETRIABLE. 2) The watchdog detects the exploit and bans M with banAddress. 3) Anyone calls retryMessage(message, false); the Bridge calls M with value and context, bypassing the ban.

Impact: The emergency ban mechanism does not stop already queued messages, so a known malicious target can still be invoked and receive bridged value.

## [Medium] Bridge.processMessage pays relayer fee even if relayer starves the call of gas

File: Bridge.sol
Function: processMessage()

When msg.sender is not destOwner the call uses _message.gasLimit as the gas parameter of ExcessivelySafeCall, but the EVM silently caps it to 63/64 of the gas the relayer actually supplied, and there is no check that gasleft() covers _message.gasLimit. If the callee runs out of gas the status becomes RETRIABLE, and the code still sends _message.fee to msg.sender. A relayer can supply just enough gas to claim the fee while causing the message to fail.

Attack path: 1) User sends a message with a fee and gasLimit of 1,000,000. 2) A relayer submits processMessage with far less gas, so the target call fails with out of gas. 3) The message becomes RETRIABLE, the relayer receives the fee and the user (or anyone) has to pay gas again with retryMessage.

Impact: Processing fees are paid without the service being delivered; users pay twice and messages can be repeatedly delayed.

## [Medium] TimelockTokenPool withdraw-by-signature is replayable (no nonce, contract or chain binding)

File: TimelockTokenPool.sol
Function: withdraw()

withdraw(address _to, bytes _sig) recovers the recipient from keccak256(abi.encodePacked('Withdraw unlocked Taiko token to: ', _to)). The hash has no nonce, expiry, contract address or chain id, and there is no used-signature tracking. The contract header says several instances are deployed for different roles, so a signature given for one pool works on every pool (and chain) where that address has a grant. Anyone who has seen the signature can call it again at any time, which forces a withdrawal of all currently unlocked tokens and pulls the cost token from the recipient via safeTransferFrom(_recipient, sharedVault, costToWithdraw) at a time chosen by the attacker.

Attack path: 1) Recipient signs a message for _to once. 2) Anyone replays withdraw(_to, sig) on the same or another pool/chain, whenever the unlocked amount grows. 3) Each replay executes _withdraw for the recipient and charges costToken from the recipient wallet.

Impact: Forced, repeated withdrawals and cost payments for the recipient at attacker chosen times (tokens go to _to); loss of control over the timing of cost token spending and the tax or price exposure that comes with it.

## [Medium] GuardianProver approval hash omits proof data, last guardian alone decides liveness bond refund

File: GuardianProver.sol
Function: approve()

The approval key is keccak256(abi.encode(_meta, _tran)) and the _proof (including _proof.data) of the guardian whose approval reaches minGuardians is the one passed to TaikoL1.proveBlock. In LibProving a top tier proof with _proof.data equal to RETURN_LIVENESS_BOND makes TaikoL1 transfer blk.livenessBond to the assigned prover and set it to zero. Earlier guardians never approved that data, so the final approver alone decides whether the assigned prover (who may have failed to prove in time) gets the 250 TKO bond back or whether it is forfeited.

Attack path: 1) minGuardians - 1 guardians approve (meta, tran). 2) The last guardian submits _proof.data = RETURN_LIVENESS_BOND (or leaves it empty). 3) proveBlock executes with that choice and the bond is refunded or kept without any quorum on it.

Impact: A single guardian can unilaterally move the liveness bond of a block, undermining the quorum and the slashing incentive for provers.

## [Medium] anchor() re-subtracts the same L1 issuance on every L2 block between syncs, collapsing gasExcess

File: TaikoL2.sol
Function: anchor()

anchor() computes the basefee through _calc1559BaseFee(config, _l1BlockId, _parentGasUsed) and stores the returned excess into gasExcess. Inside _calc1559BaseFee, numL1Blocks is _l1BlockId minus lastSyncedBlock, and issuance = numL1Blocks * gasTargetPerL1Block is subtracted from the excess. lastSyncedBlock only advances when _l1BlockId > lastSyncedBlock + BLOCK_SYNC_THRESHOLD (5), so for up to five L1 blocks the same issuance window is subtracted again on every anchor, while the stored gasExcess already had the earlier subtraction applied. The same L1 time is therefore counted cumulatively more than once, and the excess is clamped to 1 on underflow, which pins basefee at its floor.

Attack path: Within one sync window, each anchor() call from the golden touch address subtracts (L1 height minus lastSyncedBlock) times gasTargetPerL1Block from the already reduced gasExcess. After a few L2 blocks the excess is 1 and basefee_ is 1. Blocks are then produced at the minimum base fee, so a spammer can fill L2 blocks at negligible cost. This follows from the protocol's own anchor sequence and no special input is needed. The real L1/L2 block cadence was not measured.

Impact: L2 base fee drops to the minimum inside each sync window, which disables EIP-1559 congestion pricing and makes spam of L2 blocks cheap. Severity depends on how often the sync window stays open, which was not measured.

## [Medium] Top-tier same-tier re-proof asserts contestBond == 0, but the gas sentinel 1 is always stored

File: LibProving.sol
Function: proveBlock()

_createTransition sets ts_.contestBond = 1 as a gas sentinel, and _overrideWithHigherProof sets _ts.contestBond = 1 whenever a transition moves to a higher tier. In proveBlock, when _proof.tier == ts.tier and the tier is top (contestBond == 0, as for TIER_GUARDIAN), the else branch runs assert(ts.validityBond == 0 && ts.contestBond == 0 && ts.contester == address(0)). Any transition whose tier is the top tier was written by _overrideWithHigherProof, so ts.contestBond is 1 there and the assert always fails. The comment in that branch says the top tier prover re-proves, which is the intended correction path.

Attack path: The guardian set approves and proves transition T1 for parent P at tier GUARDIAN through GuardianProver.approve. Later the guardians find T1 is wrong and submit T2 for the same parent P at tier GUARDIAN. The transition id resolves to the same ts, _proof.tier equals ts.tier, the else branch reaches the top-tier assert, and the call reverts with Panic(0x01). Nothing else can replace the top-tier transition, because the top tier has contestBond 0 and cannot be contested.

Impact: A wrong guardian-proven transition cannot be corrected on-chain. The affected block either stays on a bad transition or stalls until the guardian verifier or the tier configuration is changed by the owner.

## [Medium] Guardian-proven transitions credit liveness bond to the GuardianProver contract, which cannot move TKO

## [Medium] Bridge invocation delay keeps running during a pause, so messages can execute right after unpause

## [Medium] processMessage pays the fee even when the invocation fails because the caller supplied too little gas

## [High] AssignmentHook pulls the ERC20 prover fee from a proposer-chosen coinbase, draining third-party approvals

## [Medium] SGX registration accepts any Intel-verified enclave because the MRENCLAVE/MRSIGNER allowlist is off by default

File: AutomataDcapV3Attestation.sol
Function: _verifyParsedQuote()

_verifyParsedQuote() enforces the MRENCLAVE and MRSIGNER allowlists only when _checkLocalEnclaveReport is true. That flag is a private bool with no initializer and is changed only by toggleLocalReportCheck(), so it is false after a normal deployment. ## [Medium] Proposer can avoid the 0.1% SGX_ZKVM minimum tier by choosing when to propose

File: LibProposing.sol
Function: proposeBlock()

meta_.minTier is set to getMinTier(uint256(meta_.difficulty)), where difficulty = keccak256(block.prevrandao, numBlocks, block.number) is computed inside proposeBlock(). MainnetTierProvider.getMinTier() requires SGX_ZKVM only when the value is 0 modulo 1000. For a given L1 block all of these inputs are fixed, and the block builder can see the prevrandao before it commits to including the proposal. A proposer facing the rare SGX_ZKVM outcome can decline to submit in that L1 block and submit in the next one. Attack path: 1) Proposer prepares an L2 block whose correct proof would require SGX_ZKVM. 2) It checks the prevrandao of the candidate L1 block and waits if the derived minTier is SGX_ZKVM. 3) It submits in an L1 block where the derived minTier is SGX. 4) Only an SGX proof is required, so a single compromised or attacker-registered SGX instance can prove the block.

Impact: The extra protection that SGX_ZKVM is meant to give on roughly 0.1% of blocks can be skipped at the proposer's choice, which is exactly the set of blocks where a stronger proof was intended to apply. The effect is limited to the rarity of the tier draw and the cost of waiting one block.

## [Medium] L2 gasExcess subtracts L1 issuance against lastSyncedBlock on every anchor, collapsing basefee

File: TaikoL2.sol
Function: anchor()

_calc1559BaseFee computes numL1Blocks as _l1BlockId minus lastSyncedBlock and subtracts numL1Blocks * gasTargetPerL1Block from the excess on every call. lastSyncedBlock is only advanced inside anchor() when _l1BlockId > lastSyncedBlock + BLOCK_SYNC_THRESHOLD (5). Between two syncs, each new L2 block therefore subtracts the whole issuance accumulated since the last sync again, instead of only the L1 blocks that passed since the previous anchor. The excess is clamped to 1 when the issuance exceeds it, and the clamped gasExcess is persisted. The basefee equality check at the end of anchor() enforces this same formula, so the chain accepts it as valid.

Attack path: 1) Anchors arrive on every L2 block while the L1 height advances, and for up to 5 L1 blocks lastSyncedBlock stays fixed. 2) Each anchor subtracts 1 to 6 times gasTargetPerL1Block (60,000,000) from gasExcess, so the excess falls several times faster than intended. 3) The excess reaches the clamp of 1 and basefee drops to its minimum of 1 wei for the rest of that window. 4) A spammer fills L2 blocks with cheap transactions during that window, and the same effect repeats in every sync cycle.

Impact: During every unsynced window the L2 base fee is pushed far below the bonding curve, so gas is nearly free and the EIP-1559 spam protection and fee revenue of the L2 are lost.

## [Medium] Top-tier re-proof hits assert(ts.contestBond == 0) that the override path never satisfies

## [Medium] processMessage lacks a gasleft check before the capped call, letting a relayer keep the fee

File: Bridge.sol
Function: processMessage()

Impact: The relayer collects the delivery fee without delivering the message, and delivery is delayed until another party retries it. The sender's funds are not lost, but the fee incentive is broken and delivery depends on a later retry.
