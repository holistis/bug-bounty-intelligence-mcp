# Audit report

## [Medium] sqrt() returns a result 10x too small for large-mantissa inputs with odd exponent >= 73

File: Float128.sol
Function: sqrt()

In the first (high-precision) branch of sqrt, an odd exponent is made even by aMan *= BASE and --aExp, so aMan has 73 digits and sqrt512(aMan * 10^72) always returns a 73-digit rMan. The code then does rMan /= BASE; ++rExp and only afterwards rExp = rExp / 2. Dividing rMan by 10 must add a full 1 to the halved exponent, i.e. the correct result is rExp/2 + 1. Solidity integer division truncates toward zero: for negative even rExp, (rExp+1)/2 happens to equal rExp/2 + 1, but for rExp >= 0 (aExp-72 >= 0, i.e. original exponent >= 73) (rExp+1)/2 equals rExp/2, so one power of ten is lost. Example: a = 10^71 x 10^75 (=10^146) gives aMan=10^72, aExp=74, rExp=2, rMan=10^72 -> 10^71, rExp=3 -> 3/2 = 1, result 10^72 instead of 10^73.

Attack path: Any caller computes sqrt() of a value whose L-mantissa exponent is odd and >= 73 (value >= ~10^144, inside the documented +/-3000 exponent bound), e.g. sqrt(toPackedFloat(10**71, 75)). The result is off by exactly a factor 10.

Impact: Square root is wrong by an order of magnitude (vs. a documented 0 ULP error) for a whole class of in-bounds inputs; any protocol relying on it (pricing, volatility, AMM invariants) gets silently wrong values.

## [Medium] sqrt(0) executes assembly stop(), silently terminating the entire calling contract's execution

File: Float128.sol
Function: sqrt()

sqrt contains `if iszero(a) { stop() }` inside inline assembly. stop() is not a function return: it halts the whole EVM call frame of the contract that inlined this internal library function, with success and empty returndata. All code after the sqrt call in the caller (remaining checks, state writes, return values, events) is skipped while state changes made before it are committed. The intended behaviour is to return packedFloat 0.

Attack path: A user calls an integrating contract function whose computation reaches Float128.sqrt with a zero value (e.g. sqrt of a zero balance/variance that the user can make zero). Execution stops at that point and the transaction succeeds; later require() checks or accounting updates in that function never run, and external callers decoding a return value get empty data.

Impact: Skipped validation and partial state updates in consumer contracts, broken return values for callers; a zero input is a common edge case.

## [Medium] le()/ge() return false for numerically equal values that use different (M vs L) representations

File: Float128.sol
Function: le() / ge()

le and ge only return true for equality when the raw words are identical. Otherwise both operands are scaled to L size and, when exponents are equal, le uses `retVal := lt(aMan, bMan)` and ge uses `lt(bMan, aMan)`, i.e. a strict comparison. The library itself produces several encodings of the same value: divL() forces an L mantissa for any exponent (divL(1,1) = 10^71 x 10^-71 while toPackedFloat(1,0) = 10^37 x 10^-37), toPackedFloat keeps 72-digit mantissas as L even for exponents <= -52, and add/sub can leave unnormalized results. For such pairs, after scaling, mantissas and exponents are equal, so le and ge both return false although the values are equal.

Attack path: An integrator checks `require(x.le(limit))` or `x.ge(threshold)` where one side comes from divL (or another L-forced/unnormalized path) and the other from toPackedFloat/div. When the values are exactly equal the check fails (or the inverse branch is taken).

Impact: Boundary checks (limits, thresholds, solvency/price bounds) behave incorrectly at equality, causing wrong reverts or wrong branching in consuming contracts.

## [Medium] ln() does not reject negative or zero inputs: ln(-x) returns ln(x) and ln(0) returns a finite garbage value

File: Ln.sol
Function: ln()

ln() extracts only the mantissa (and MANTISSA_MASK excludes the sign bit) and the exponent; the MANTISSA_SIGN_MASK is never checked and there is no check for zero. For a negative input the computation proceeds on |x| and returns ln(|x|) (ln(-1) even hits the early `return 0`). For input 0 (mantissa 0, exponent -8192) the else branch runs with mantissa 0: k=3, q1=q2=q3=7, z_int = 10^76 -> z = 1, and the Taylor series plus m10*ln10 terms produce a finite large negative number instead of reverting. sqrt() by contrast reverts on negative input.

Attack path: A consumer passes a value that can become negative or zero (e.g. a difference or a user-supplied ratio) to Ln.ln. Instead of reverting, a plausible-looking number is returned and used in further math.

Impact: Mathematically undefined inputs yield silent wrong results (sign lost, or a bogus finite log of zero), which can corrupt pricing/interest computations that rely on ln.

## [Medium] add()/sub() subtraction path leaves 38-digit results with exponent > MAXIMUM_EXPONENT unnormalized

File: Float128.sol
Function: add() / sub()

In the subtraction branch, normalization is skipped whenever `addition` already lies in [MIN_M_DIGIT_NUMBER, MAX_M_DIGIT_NUMBER] or in the L range; the only follow-up (`else if`) converts L-sized results with small exponents to M. There is no counterpart that converts an M-sized (38-digit) result whose exponent is > MAXIMUM_EXPONENT (-18) into L, unlike toPackedFloat which does exactly that. In the L path r = aExp - 4, so cancellation of two L numbers with exponent around 0 can give a 38-digit `addition` at exponent -4, which is returned as an M number with exponent -4. Additionally the else-if uses `rExp < ZERO_OFFSET - 18 - 34`, keeping an L result at exponent exactly -52 as L while mul/div/add produce M at that point.

Attack path: Compute a.sub(b) (or add with opposite signs) for two L numbers that agree in their first 34 significant digits, e.g. a = toPackedFloat(10**71 + 10**33, 0), b = toPackedFloat(10**71, 0). The result is M 10^37 x 10^-4 instead of the canonical L 10^71 x 10^-38.

Impact: Breaks the library's normalization invariant (unique representation, >=18 decimals for M); eq() against the canonical encoding of the same value returns false and le/ge misbehave, leading to wrong branching in consumers.

## [Medium] eq() compares raw words while toPackedFloat/divL produce multiple encodings of the same value

File: Float128.sol
Function: eq() / toPackedFloat()

eq() is `packedFloat.unwrap(a) == packedFloat.unwrap(b)`, which is only correct if every value has a single canonical encoding. toPackedFloat leaves any 72-digit mantissa as L regardless of exponent (third branch has no exponent check), so toPackedFloat(10**71, -52) (L) and toPackedFloat(10**37, -18) (M) encode the same value differently, and divL always returns L even for small exponents. Comparing such values with eq() returns false, and gt/lt treat them as equal, so eq is inconsistent with the ordering functions.

Attack path: A consumer builds one value via toPackedFloat with a 72-digit mantissa (or via divL) and another via div/mul/toPackedFloat with a 38-digit mantissa, then uses eq() to check equality; the check fails although the numbers are identical.

Impact: Equality checks fail for equal numbers, causing wrong reverts or skipped logic in contracts using the library.

## [High] sqrt(0) runs stop() and halts the caller's entire transaction instead of returning zero

File: Float128.sol
Function: sqrt()

Inside sqrt the zero case is handled with `if iszero(a) { stop() }`. Float128.sqrt is an internal library function that is inlined into the calling contract, so the EVM STOP opcode does not leave the function: it ends the whole call frame with success and empty return data. Nothing after the sqrt call in the integrator's function runs (checks, accounting, events, transfers), while state changes made before the call stay committed. The negative-input path correctly reverts, and the zero path was clearly meant to return a zero packedFloat (r is never assigned), so this is a wrong early exit and not an intended abort.

Attack path: 1. An integrating contract computes sqrt of a quantity that can be zero (zero variance, zero reserve, zero amount). 2. A user or attacker makes that quantity zero. 3. sqrt(packedFloat.wrap(0)) executes stop(). 4. The outer function returns success with empty returndata: later statements are skipped, earlier writes persist. External callers that decode a return value revert on decode, callers using low-level call see success.

Impact: Silent partial execution of any transaction that takes the square root of zero: skipped invariant checks, unpaid or unrecorded steps after already-committed transfers, or a forced revert/DoS on callers that expect return data. The integrator cannot guard against it with try/catch because the call frame ends successfully.

## [Medium] sqrt of L-mantissa numbers with odd exponent >= 73 returns a result 10x too small

File: Float128.sol
Function: sqrt()

In the large-number branch, after making the exponent even, rMan = Uint512.sqrt512(aMan * 10^72) has 73 digits whenever the odd-exponent correction aMan *= BASE was applied. The code then does `rMan /= BASE; ++rExp;` and only afterwards `rExp = rExp / 2`. The increment is meant to compensate the removed digit, but it is applied before halving, so it only adds half a step, and Solidity signed division truncates toward zero. For negative rExp the odd value rounds up and the compensation survives; for rExp >= 0 (aExp - 72 >= 0, i.e. odd unbiased exponent >= 73, values from about 1e144 upward) it is truncated away and the mantissa stays divided by 10 with the exponent not raised. The correct update would be rExp += 2 before halving. The fuzz test for sqrt clamps the exponent to [-74, 1] with a TODO, so this region is never exercised.

Attack path: 1. Caller builds a = toPackedFloat(1, 146), stored as L mantissa 1e71 with unbiased exponent 75. 2. sqrt(a): exponent 75 is odd, so aMan = 1e72 and aExp = 74. 3. sqrt512(1e72 * 1e72) = 1e72 > MAX_L_DIGIT_NUMBER, so rMan = 1e71 and rExp = (74 - 72) + 1 = 3. 4. rExp / 2 = 1 (truncation), so the result is 1e71 * 10^1 = 1e72 instead of sqrt(1e146) = 1e73. Every L number with odd exponent from 73 up to the 3000 limit is affected.

Impact: Wrong square root, off by a whole factor of 10 (not an ULP error), for about half of all large inputs inside the documented exponent range. Any value or risk computation that consumes the result is silently wrong by 10x.

## [High] add/sub return a 72-digit mantissa without the L flag after near-cancellation of large numbers

File: Float128.sol
Function: add()/sub()

In the L branch the result exponent r is built from the masked exponent fields only, so it carries no L flag. The flag is added only inside the 'not already normalized' branch (isResultL) or in the same-sign addition path. For a subtraction whose 76-digit aligned difference `addition` has exactly 72 digits, the first condition treats it as already normalized and skips that branch; the `else if (addition >= MIN_L_DIGIT_NUMBER && rExp < ZERO_OFFSET - 18 - DIGIT_DIFF_L_M)` only demotes to M when biased rExp < 8140. For rExp >= 8140 (unbiased result exponent >= -52, operands of magnitude roughly 1e23 and up) nothing sets the flag, so r | addition is a 72-digit mantissa stored as an M number. Canonical L inputs reach this, not only odd encodings. A mirror symptom is a 38-digit difference left as M with an exponent above -18; that one is exact and tolerated, the 72-digit one is not.

Attack path: 1. a = toPackedFloat(10005000000000000000000000000000000000, -7) (1.0005e30) and b = toPackedFloat(10^37, -7) (1e30); both become L with mantissas 1.0005e71 and 1e71, exponent -41. 2. sub(a, b): equal exponents, both mantissas times 1e4, r exponent -45, addition = 5e71 (72 digits). 3. Normalization is skipped and the else-if does not fire because biased rExp 8147 is not below 8140. 4. Result is mantissa 5e71, exponent -45, L flag clear. 5. Any later mul/add/div/lt/le/gt/ge/ln/sqrt treats it as a 38-digit M number and multiplies the 72-digit mantissa by 1e34 or 1e38 in assembly, which wraps modulo 2^256 without reverting.

Impact: Silent garbage in all later arithmetic and comparisons on the result whenever two large numbers (about 1e23 and up, for example 100k tokens at 18 decimals) agree on their first 3 to 5 digits and are subtracted. This can mis-price or mis-account in any protocol that computes such differences, and the fuzz tests do not hit it because random operand pairs are almost never this close.

## [Medium] eq/le/ge give false for equal values stored as M and as L (divL, toPackedFloat)

File: Float128.sol
Function: le()/ge()/eq()

eq is a raw uint256 comparison. le and ge return true only if the raw words are equal, otherwise they scale M operands to 72 digits and, at equal exponents, compare mantissas with the strict lt/gt, so two encodings of the same value make lt, gt, le, ge and eq all return false (trichotomy is broken). The public API produces such twins: divL always forces the L flag (`Loperation := or(gt(rExp,maxExp), rL)`) while div picks M for small exponents, and toPackedFloat gives every 72-digit mantissa the L flag regardless of the exponent (last else-if), whereas the normalization branch gives M for small exponents.

Attack path: 1. x = div(toPackedFloat(1,0), toPackedFloat(2,0)) is M (5e37, exp -38); y = divL(toPackedFloat(1,0), toPackedFloat(2,0)) is L (5e71, exp -72). 2. Alternatively x = toPackedFloat(5, -1) is M and y = toPackedFloat(5e71, -72) is L. 3. Both represent 0.5, but eq(x,y), le(x,y), ge(x,y), lt(x,y) and gt(x,y) are all false.

Impact: A protocol check such as require(ge(balance, required)) or an equality/tie check fails or passes depending on how the operands were produced, for exactly equal values.

## [Medium] ln accepts zero and negative inputs and returns finite values instead of reverting

File: Ln.sol
Function: ln()

ln() reads only the L flag, mantissa and exponent from the input and never tests the sign bit or a zero mantissa (unlike Float128.sqrt, which reverts for negatives, and div, which reverts for zero). A negative input is processed as its absolute value, so ln(-5) returns ln(5). For zero (packed value 0, exponent -8192) ln_helper takes the else branch with m10 = 38 - 8192, mantissa 0 passes through calculateQ1/Q2/Q3 as q1=q2=q3=7, z becomes 1.0, and the final sum returns a finite negative number of about -1.878e4 (derived by hand, not executed) instead of reverting.

Attack path: 1. A protocol passes a user-influenced packedFloat to Ln.ln. 2. The user supplies a negative value or zero. 3. ln() returns ln(|x|) or about -18781 without reverting. 4. The caller uses the value as a valid logarithm.

Impact: Silent wrong results for domain errors in every consumer that relies on the library to reject them, for example a zero input producing a large but finite number that is then used in pricing or fee math.

## [High] sqrt(0) executes STOP inside the library and silently halts the calling transaction

File: Float128.sol
Function: sqrt()

sqrt() opens an assembly block that reverts for a negative word and then runs 'if iszero(a) { stop() }' for a zero word. Float128.sqrt is internal, so this stop() is compiled into the calling contract's own bytecode and executes a STOP opcode for the whole call frame. The call then ends with success and empty returndata, and no code after the sqrt() call runs, even though zero is a valid non-negative input whose root is 0. A zero word is produced by sub(x,x) (r is set to 0 when addition is zero), by mul with a zero factor (returns wrap(0)), and by toPackedFloat(0,e).

Attack path: A consumer contract computes v = sub(x,x) or receives any zero packedFloat and calls Float128.sqrt(v) inside a function that afterwards updates storage, transfers, or emits events. Execution reaches iszero(a), STOP runs, and the function returns nothing while the transaction reports success. State writes before the call persist and later writes are skipped. If the sqrt call is inside an external call, the caller's ABI decoding of the empty returndata reverts instead.

Impact: Silent success with skipped logic whenever a root of zero is needed. A check or bound that depends on sqrt() is skipped rather than evaluated to 0, and the partial state is committed. The path is reachable with ordinary zero-variance inputs, not only with adversarial values.

## [Medium] sqrt() L-path divides the mantissa by 10 but adds only 1 to the exponent before halving, so the result is 10x too small

File: Float128.sol
Function: sqrt()

In the L branch sqrt() takes aExp as the even unbiased exponent after the parity fix-up, computes rMan = sqrt512(aMan * 10^72) and sets rExp = aExp - 72. When rMan > MAX_L_DIGIT_NUMBER the code does rMan /= BASE and ++rExp, and only afterwards rExp = rExp / 2 (signed division, truncating toward zero). Dropping one decimal digit of the mantissa means the final value is multiplied by 10, which needs +2 on rExp before the halving; +1 is only half a step. The M-branch of the same function (lines 824-829) halves first and then adds 1 to the final exponent, which is correct. The error is one-sided: for positive rExp the truncation drops the extra step, while for negative rExp the truncation happens to compensate.

Attack path: Caller builds an L-size packedFloat with mantissa 10^72 - 1 (72 nines, L flag set) and exponent 75, so the value is about 1e147. Inside sqrt(), aMan becomes (10^72 - 1) * 10 (odd exponent fix-up), aExp becomes 74, and rMan = sqrt512(aMan * 10^72) is about 3.1623e72, which exceeds MAX_L_DIGIT_NUMBER. The code divides rMan by 10 to about 3.1623e71 and rExp goes 2 -> 3 -> 3/2 = 1, so the decoded result is about 3.1623e71 * 10^1 = 3.1623e72. The correct root is about 3.1623e73.

Impact: Every L-size input with odd unbiased exponent e >= 73 (values of roughly 1e144 and above) returns a root that is 10 times too small without any revert. Any consumer that uses sqrt() on such large values gets a silently wrong magnitude.

## [Medium] le() and ge() return false for equal values stored once as M-size and once as L-size

File: Float128.sol
Function: le() / ge() (eq() has the same raw-word semantics)

eq() compares raw packed words, and le()/ge() return true early only when the raw words are identical. When two operands hold the same value in different encodings (one with a 38-digit M mantissa, one with a 72-digit L mantissa), the code scales the M mantissa by 10^34 and subtracts 34 from its exponent, reaches the same-sign branch with eq(aExp, bExp) true, and then uses the strict lt(aMan, bMan) (for le) or lt(bMan, aMan) (for ge). With equal mantissas both return false. The library itself produces mixed encodings: divL(1,1) returns the L-size form of 1 (mantissa 10^71, exponent -71, L flag), while toPackedFloat(1,0) is the M-size form (10^37, exponent -37). sqrt() also always returns an M-size word, even when the result exponent is above -18 where toPackedFloat would choose L, so the same mismatch can occur there.

Attack path: Caller computes one = Float128.divL(toPackedFloat(1,0), toPackedFloat(1,0)). Caller then evaluates Float128.le(toPackedFloat(1,0), one) as a bound check 'value <= limit' where both sides are exactly 1. The raw words differ because of the L flag, so the early return is skipped, both mantissas align to 10^71 with equal exponents, lt(10^71, 10^71) is false, and le() returns false.

Impact: A comparison that should hold for equal values returns false silently (ge() fails the same way, and eq() reports two equal values as different). Bounds and threshold checks built on these functions can reject valid inputs or behave inconsistently depending on which operation produced the operand.

## [Medium] ln() ignores the sign bit, so ln(-x) silently returns ln(|x|) instead of reverting

File: Ln.sol
Function: ln()

ln() reads mantissa := and(input, MANTISSA_MASK) and exponent from EXPONENT_MASK. MANTISSA_MASK covers the low 240 bits and excludes the sign bit at bit 240 (MANTISSA_SIGN_MASK in Float128), and nothing in ln() or ln_helper() tests that bit. The sign is therefore discarded and the magnitude goes through the series. The sibling function Float128.sqrt() reverts on the sign bit ('float128: squareroot of negative'), so the library handles the domain inconsistently.

Attack path: Caller computes Ln.ln(Float128.toPackedFloat(-2, 0)). toPackedFloat sets the sign bit and stores mantissa 2*10^37 with exponent -37. ln() masks the sign away, computes the log of 2, and returns about 0.693147 with no revert.

Impact: A negative input produces a plausible positive-looking log. A consumer that expects the library to reject negative inputs (as it does for sqrt) accepts wrong values silently, for example in a formula that takes ln of a negative ratio or return.

## [Medium] ln(0) takes the normal series path with mantissa 0 and returns a finite number instead of reverting

File: Ln.sol
Function: ln() / ln_helper()

ln() only short-circuits for the input 1 (exponent -37 with mantissa 10^37). For the zero word the exponent is 0 - 8192 = -8192 and the mantissa is 0, so the guard is false. ln_helper() takes the else branch with m10 = 38 - 8192 = -8154, sets mantissa = 0 times 10^38 times 8, and calculateQ1/Q2/Q3(0) return q1 = q2 = q3 = 7 with mantissa 0. intermediateTermAddition then sets z_int = 10^76 - 0 and z = toPackedFloat(10^37, -37) = 1, and the 15-term series evaluated at z = 1 is a truncated harmonic sum of about 3.32 rather than a rejection. finalTermAddition adds k*ln2 and the q-terms, subtracts m10*ln10, and negates, so the result is a finite negative number of roughly -18,780 (hand estimate, not executed).

Attack path: Caller computes a log of a ratio whose numerator is zero, for example ln(0) of a value that was never initialized or an intermediate that became zero through sub(x,x). The call returns a finite packedFloat of about -18,780 without reverting.

Impact: A silent wrong value for an undefined input. A consumer that feeds this result into a threshold check gets a large finite number that can pass or fail the check arbitrarily.

## [Medium] mul() and div() do not bound the biased exponent, so out-of-range results wrap modulo 2^14 (underflow becomes huge, overflow becomes tiny)

File: Float128.sol
Function: mul() / div()

mul() computes rExp = biasedA + biasedB - 8192 as a plain uint256 and then writes shl(EXPONENT_BIT, rExp). The exponent field is only 14 bits (bits 242 to 255), and no range check is made before the shift, so a negative result (a wrapped uint256) or a result above 16383 loses its high bits silently. The unsigned comparison Loperation := gt(rExp, maxExp) treats a wrapped negative as huge and takes the L-branch, so the wrap is not caught there either. div() has the same pattern (rExp = aExp + 8192 - bExp) and the L-path adjustments repeat it.

Attack path: Two M-size packedFloats a = b = 10^37 * 10^-4100 (packed exponent -4100, values about 1e-4063 each). The true product exponent is -8200 (mantissa-scale -8197 after the L conversion), below the minimum of -8192, so it should underflow. mul() computes biased rExp = 8192 - 8200 = -8, the L-branch adds 3, the field becomes 16379 and decodes to exponent 8187, so the returned value is about 1e8258. Symmetrically a = b = 10^37 * 10^4100 should overflow but the field wraps to decoded exponent -8181, returning a value of about 1e-8110.

Impact: Products or quotients beyond the representable range silently flip between huge and tiny. A tiny product becomes an enormous number that can pass upper-bound checks, and a huge one becomes a tiny number that can pass lower-bound checks. Such magnitudes need extreme exponents, but the library accepts them and never signals the error.

## [Medium] sqrt() returns a result 10x too small for odd exponents >= 73 when the integer root overflows 72 digits

File: Float128.sol
Function: sqrt()

In the big-exponent branch, sqrt() first makes the working exponent even by multiplying aMan by BASE and decrementing aExp when the exponent is odd. For any such input the scaled mantissa is 10^72 or more, so rMan = sqrt512(aMan * 10^72) reaches 10^72 and the overflow correction 'rMan /= BASE; ++rExp' runs before the halving. The halving 'rExp = (rExp) / 2' is Solidity signed division, which truncates toward zero, so for a positive odd value (e'' - 71) it returns (e'' - 72) / 2 instead of (e'' - 70) / 2, one exponent step too low. The result is therefore divided by 10 whenever the adjusted exponent is positive. Negative exponents are not affected because truncation toward zero goes the other way there. Concrete case: canonical L input mantissa 10^71 with exponent 73 (value 10^144) makes rMan = 10^72, the code produces mantissa 10^71 with exponent 0 (value 10^71), and the correct value is 10^72.

Attack path: No privileged actor is needed. Any protocol or user that calls sqrt() on a value whose exponent after normalization is odd and at least 73 (large-mantissa inputs) receives a result that is ten times too small. Values can also be produced by mul() or div() and then passed to sqrt().

Impact: Silent wrong sqrt result by a factor of 10 for inputs inside the documented bounds (exponent far below 3000, at most 72 significant digits). This contradicts the README claim that sqrt has a maximum error of 0 ULP. A consumer that uses sqrt for pricing, collateral or distance math is understated by an order of magnitude with no revert.

## [Medium] add()/sub() of two large-mantissa values that cancel to 72 digits returns a word without the L flag

File: Float128.sol
Function: sub()

Both add() and sub() build the result exponent r from the masked exponent bits only, so MANTISSA_L_FLAG_MASK is never copied from the operands. In the isSubtraction normalization branch the flag is set only when the mantissa must be reduced. When the aligned difference is in the L range [10^71, 10^72) the first block is skipped, and the else-if that would convert it to M runs only when rExp < 8140. For two L operands with exponent of at least -48 that condition is false, so the result keeps no L flag while carrying a 72-digit mantissa. Concrete trace: a = (L, 10^71 + 10^67, exponent 0) and b = (L, 10^71, exponent 0). The aligned difference is 10^71 with raw exponent 8188, and the returned word is an M-flagged 72-digit mantissa for value 10^67. The canonical encoding of 10^67 is (L, 10^71, exponent -4), which differs only in the flag.

Attack path: Any caller subtracting two large-value numbers (or adding numbers of opposite sign) whose mantissas agree in their first 67 digits receives the malformed word. The next operation on that word, such as mul() or a comparison, treats it as a 38-digit mantissa.

Impact: The library returns a value that is not a valid packedFloat encoding, with no revert. Later mul() multiplies a 72-digit mantissa as if it were 38 digits, so 256-bit products wrap silently, and eq(), lt() and le() compare the wrong representation. The numeric error is large and is not a rounding issue.

## [Medium] ln() does not reject zero or negative inputs: sign bit is dropped and zero returns a finite value

File: Ln.sol
Function: ln()

ln() extracts the mantissa with and(input, MANTISSA_MASK), where MANTISSA_MASK covers bits 0 to 239 and excludes the sign bit at bit 240, and never reads MANTISSA_SIGN_MASK. So ln(-x) computes ln(x) with no error. For zero the word is 0, so the exponent becomes -8192 and the only special case in ln() (exponent -37 with mantissa 10^37, or exponent -71 with mantissa 10^71) does not match. ln_helper then runs the normal path with mantissa 0 and m10 = 38 - 8192 = -8154, and returns a finite large negative number (hand-derived as roughly -18,781, not verified by running code). Float128.sqrt() reverts on negative inputs with 'float128: squareroot of negative', but ln() has no equivalent domain check.

Attack path: A protocol that takes ln() of a quantity that can be zero or negative, such as a balance difference, a price change or a ratio computed from user-supplied values, gets a finite, plausible-looking result instead of a revert.

Impact: Invalid inputs produce wrong finite logarithms and a negative input silently loses its sign, so downstream math is wrong without any signal. This matters for any consumer whose safety depends on ln() reverting on bad input.

## [Medium] toPackedFloat() stores L-range mantissas with exponent <= -18, so equal values get two encodings and le()/ge()/eq() misjudge them

File: Float128.sol
Function: toPackedFloat()

toPackedFloat() moves an M-range mantissa to L only when the exponent is above MAXIMUM_EXPONENT (-18). For an L-range mantissa (the branch that just sets MANTISSA_L_FLAG_MASK) it never checks the exponent, so the library produces a non-canonical word. Example: toPackedFloat(10^71, -71) and toPackedFloat(10^37, -37) both represent 1.0 but have different words. In le() and ge() both operands are scaled to L and then compared with lt(aMan, bMan), which is false for equal mantissas, so le(a, b) and ge(a, b) return false for equal values. eq() compares raw words and also returns false. The README states that a number must have only one normalized representation.

Attack path: A caller builds a bound or constant from a 72-digit mantissa with a negative exponent (for example toPackedFloat(10^71, -71)) and checks it with le() or ge() against a value encoded through the 38-digit path. The check returns false for equal values, which can reject a valid input or flip an inequality guard.

Impact: Comparison results for equal values depend on how the value was encoded, so bounds checks written with le() or ge() can be wrong. The effect is a logic error in comparisons and not an arithmetic overflow.

## [High] add() and sub() drop the L flag when a 72-digit subtraction result has exponent >= 8140, leaving a corrupt word

File: Float128.sol
Function: add() and sub()

In the L path of add() and sub(), r is built from the masked exponent of aExp with no MANTISSA_L_FLAG_MASK. Normalization sets the L flag only inside the first if (digit count outside both the M and the L range), and the else-if converts to M only when addition >= MIN_L_DIGIT_NUMBER and rExp < 8140. When addition is a valid 72-digit L-range value and rExp is 8140 or more, neither branch runs, so r | addition holds a 72-digit mantissa with the flag clear. The decoded value is still correct, because the exponent was already reduced by 4 for the 76-digit scale, but the word is not a valid M encoding. The strict < 8140 comparison also leaves rExp == 8140 in the gap.

Attack path: A caller computes sub(a, b) on two L-encoded numbers with exponent 0 or higher, that agree in their first four digits: a = toPackedFloat(10001 * 10^67, 0) and b = toPackedFloat(10^71, 0). The difference 10^67 is returned as a 72-digit mantissa with no L flag. The next operation on that word takes the M path, for example mul(result, 2) or add(result, x), which multiplies the 72-digit mantissa by 10^38 or by another 38-digit mantissa; the product exceeds 2^256 and wraps, so the output is arbitrary with no revert.

Impact: Silent wrong arithmetic from ordinary inputs in the core add and sub path: an exact difference of two large L values becomes garbage after the next operation, which can corrupt a price, balance or interest delta without any error.

## [Medium] sqrt() of an L value with odd decimal exponent >= 73 returns a result 10x too small

File: Float128.sol
Function: sqrt()

In the big branch, an odd aExp is fixed by multiplying aMan by 10 and decrementing aExp, so aExp becomes even and rExp = aExp - 72 is even. When rMan > MAX_L_DIGIT_NUMBER the code runs rMan /= BASE and ++rExp, and only then runs rExp = rExp / 2 with signed truncation toward zero. The increment must happen after halving, because the correct exponent is (aExp - 72) / 2 + 1. For a non-negative rExp the truncation discards the +1 (for example (2 + 1) / 2 = 1 where 2 is expected), so the decimal exponent is one short and the result is 10 times too small. For negative rExp the truncation happens to give the right answer, which is why small inputs are unaffected.

Attack path: A caller passes toPackedFloat(10^71, 73), which is an L word with value 10^144. aExp is 73, odd, so aMan becomes 10^72 and aExp becomes 72. sqrt512 returns 10^72, the branch divides rMan to 10^71 and sets rExp to 0 then 1, and 1 / 2 = 0, so the result is 10^71 instead of 10^72.

Impact: Silent 10x error in sqrt for L inputs with odd exponent 73 or more (values of about 10^144 and up). Any protocol that derives a fee, collateral or rate from such a sqrt would be off by a factor of ten with no revert.

## [Medium] Exponent field is never range-checked, so toPackedFloat() and mul() silently wrap out-of-range exponents

File: Float128.sol
Function: toPackedFloat() and mul()

toPackedFloat() writes shl(EXPONENT_BIT, add(exponent, ZERO_OFFSET)) after normalization without checking the documented -8192..8191 range. mul() computes rExp = stored(a) + stored(b) - 8192 with no bound, and then ORs shl(EXPONENT_BIT, rExp), which keeps only the low 14 bits. Normalization can push an in-range argument outside the range: toPackedFloat(1, -8180) gets an M-shift of -37, so the exponent becomes -8217, which is stored as 16359 and decodes as exponent 8167. Products whose exponents add past 8191 wrap in the other direction, and no path reverts.

Attack path: An integrator calls toPackedFloat(1, -8180), which is an in-range argument, and later uses the result as a small factor. Alternatively two L values with exponent 5000 each are multiplied with mul(); the product exponent of 10071 wraps. Nothing reverts in either case.

Impact: A tiny value silently becomes a huge one, and a huge product silently becomes a tiny one. The hand trace gives about 10^8167 for the first example and about 10^-6313 instead of 10^10071 for the second. Any pricing, interest or collateral computation that depends on such magnitudes would be wrong without an error.

## [Medium] ln() ignores the sign bit, so ln of a negative input returns ln of its absolute value

File: Ln.sol
Function: ln()

ln() reads the mantissa with and(input, MANTISSA_MASK), which drops bit 240 (MANTISSA_SIGN_MASK), and it never inspects the sign before calling ln_helper(). Float128.sqrt() reverts on a negative argument, so ln is inconsistent with the rest of the library. The result for a negative input is a plausible-looking logarithm of |x| with no revert and no sign flag.

Attack path: An integrator computes ln of a signed quantity such as a price delta or a ratio whose sign is negative. Because ln() masks the sign, it returns ln(|x|) instead of reverting, and the integrator treats that number as a valid log.

Impact: Silent wrong value in any protocol that takes the log of a signed quantity, with no error to alert a caller.

## [Medium] ln(0) does not revert and returns a finite value of about -18780

File: Ln.sol
Function: ln() and ln_helper()

ln() special-cases only the exact value 1. For input 0 the mantissa is 0 and the exponent is 0 minus 8192. ln_helper() takes the small-number branch, multiplies the mantissa 0 by 10^38, and calculateQ1, Q2 and Q3 then return their multipliers with mantissa 0. intermediateTermAddition() rescales z = 10^76 - 0 to exactly 1, sums the 15-term series to H_15, and finalTermAddition() uses m10 = 38 - 8192 = -8154. The result is a finite number near -18780 instead of a revert. Unlike div(), which reverts on a zero divisor, ln has no zero check. This is a hand trace and was not run.

Attack path: A zero balance, zero rate or zero ratio is passed directly to ln(). The call succeeds and returns a finite negative number that looks like a valid logarithm.

Impact: Silent wrong result instead of an error. A downstream calculation proceeds with a fabricated value, which can mis-price or mis-accrue an amount.

## [Medium] le() and ge() return false for equal values that have different encodings

File: Float128.sol
Function: le() and ge()

The early return only compares the raw words. For two positive or two negative operands whose aligned exponents are equal, le() sets retVal from lt(aMan, bMan) and ge() sets it from lt(bMan, aMan), which is false when the aligned mantissas are equal. Equal values can have different words: toPackedFloat(10^37, -37) encodes 1 in M form and toPackedFloat(10^71, -71) encodes 1 in L form, and both decode to 1. eq() compares raw words too. divL() and the flag gap in add and sub can also produce L words with exponent at or below -18, which are the non-canonical forms in question.

Attack path: A caller checks require(le(x, cap)) or ge(balance, price) where x equals the bound in value but uses a different encoding. The check fails. lt and gt both return false for the same pair, so the three comparisons are mutually inconsistent.

Impact: Wrong comparison outcome on equal values, which can wrongly reject a valid amount or wrongly pass or fail a threshold check in the calling protocol.
