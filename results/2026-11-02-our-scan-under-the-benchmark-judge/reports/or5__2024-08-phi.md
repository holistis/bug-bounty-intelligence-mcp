# Audit report

## [Medium] Public _addCredIdPerAddress/_removeCredIdPerAddress let anyone corrupt a holder's position index, blocking full exit

File: Cred.sol
Function: _removeCredIdPerAddress()/_addCredIdPerAddress()

Both bookkeeping helpers are declared `public` with no access control, although they are meant to be called only from `_updateCuratorShareBalance`. Anyone can call `_removeCredIdPerAddress(credId, victim)` and delete the victim's entry from `_credIdsPerAddress`, `_credIdsPerAddressCredIdIndex` and `_credIdsPerAddressArrLength`. `_credIdExistsPerAddress[victim][credId]` stays true and `shareBalance` is unchanged. When the victim later sells down to exactly 0, `_updateCuratorShareBalance` calls `_removeCredIdPerAddress` again. That call reverts with `EmptyArray`, `IndexOutofBounds` or `WrongCredId` because the index mapping is now 0 or points at a different credId. An attacker can also call `_addCredIdPerAddress` with arbitrary arguments to push duplicates or overwrite the index mapping, which corrupts later removals.

Attack path: 1. Victim buys shares of cred X. 2. Attacker calls Cred._removeCredIdPerAddress(X, victim). 3. Victim tries to sell all of their shares. `_handleTrade` or `_executeBatchTrade` reverts in `_removeCredIdPerAddress`. 4. The victim can only sell down to 1 share, and cannot exit fully until they repair the list by calling `_addCredIdPerAddress` themselves.

Impact: Griefing that freezes the last shares of any holder's position. `getPositionsForCurator` also returns wrong data. Attackers can target any holder at negligible cost.

## [Medium] Anyone can reset a curator's share lock by buying 1 share for them, so they can never sell

File: Cred.sol
Function: buyShareCredFor()/batchBuyShareCred()

`_handleTrade` and `_executeBatchTrade` set `lastTradeTimestamp[credId][curator_] = block.timestamp` on every buy. `curator_` is an arbitrary third-party address supplied by the caller in `buyShareCredFor` and `batchBuyShareCred`. The lock check on sells uses the same mapping (`block.timestamp <= lastTradeTimestamp + SHARE_LOCK_PERIOD`). A third party can therefore extend a victim's lock at will.

Attack path: 1. Victim holds shares. 2. Every few minutes (less than 10) the attacker calls buyShareCredFor(credId, 1, victim, 0). 3. The victim's sells keep reverting with ShareLockPeriodNotPassed.

Impact: A victim's shares can be frozen indefinitely, for example during a price crash. The attacker pays only the price of 1 share plus fees, and the victim receives that share.

## [Medium] Share lock bypass: refund callback reenters before lastTradeTimestamp is updated; no nonReentrant on single trades

File: Cred.sol
Function: _handleTrade()

In the buy path, `_handleTrade` updates the share balance and supply and then sends the excess payment to `_msgSender()`. Only after that does it set `lastTradeTimestamp[credId_][curator_]`. `_handleTrade` has no `nonReentrant` (only the batch executor has it). In the refund callback the caller still has the old timestamp. They can call `sellShareCred` and sell the shares just bought, because the lock check passes against the stale timestamp.

Attack path: 1. A contract that already holds shares of cred X, with an expired lock, calls buyShareCred with msg.value above the price. 2. In receive(), the contract calls sellShareCred for the newly bought amount, and the lock passes. 3. Within one transaction it can also call CuratorRewardsDistributor.distribute while holding the inflated share count.

Impact: The 10-minute SHARE_LOCK_PERIOD, which exists to stop flash or just-in-time positions, is defeated. Combined with the distribute snapshot, this lets an attacker capture rewards without being exposed to price risk.

## [Medium] Curator rewards are distributed on a spot snapshot of balances; anyone can trigger it after buying shares (JIT capture)

File: CuratorRewardsDistributor.sol
Function: distribute()

`balanceOf[credId]` accumulates rewards over time. `distribute` is permissionless and splits the whole balance pro-rata over current `getShareNumber` values at call time, with no time-weighting or checkpointing. A buyer can acquire a large share of the supply right before calling `distribute`. They receive a proportional part of all rewards accrued by earlier holders, and the callback lock bypass makes this possible in one transaction.

Attack path: 1. A cred accumulates rewards in the distributor. 2. The attacker buys many shares (up to supply 999). 3. The attacker calls distribute(credId) and receives a large part of the accumulated pool as PhiRewards balance. 4. The attacker sells the shares, or sells after the lock.

Impact: Long-term curators are diluted and the attacker steals a large part of the pooled rewards. The attacker's cost is only the curve spread and fees. A large pool makes this profitable.

## [Medium] Claims never enforce one-mint-per-user; quantity and imageURI are not covered by the signature or merkle leaf

File: PhiFactory.sol
Function: signatureClaim()/merkleClaim()/_validateAndUpdateClaimState()

`_validateAndUpdateClaimState` writes `credMinted` and `artMinted` but never reads them, so there is no already-claimed check. The signed `claimData` (expiresIn, minter, ref, verifier, artId, chainid, data) has no nonce and excludes `quantity` and `imageURI`. The merkle leaf is only `(minter, leafPart)`. One valid signature or proof can be replayed any number of times until expiry, and the caller chooses the quantity. Any third party can also use the signature or proof to mint for the minter with an arbitrary `imageURI` and `ref_`. That overwrites `advancedTokenURI[tokenId][minter]` and `minterData`.

Attack path: 1. A user obtains a valid signature or merkle proof, or a third party observes the public claim calldata. 2. The caller calls claim/signatureClaim/merkleClaim repeatedly, with large quantity, up to art.maxSupply. 3. The caller sets a malicious imageURI for the minter and picks a `ref_` address of their own.

Impact: The 'one claim per eligible address' guarantee is not enforced. The supply can be exhausted by a single address. Minters' token URIs can be defaced.

## [Medium] createArt signature does not bind CreateConfig or caller; signed credData can be replayed by anyone to create arts with arbitrary params

File: PhiFactory.sol
Function: createArt()

The signer signs only `(expiresIn, uri, credData)`. The caller supplies `CreateConfig` (artist, receiver, maxSupply, mintFee, start/end time, soulBounded) outside the signature, and nothing ties the signature to `msg.sender`. There is no nonce, so the same signature can be reused until `expiresIn`. A third party who sees a signed payload in the mempool, or in earlier calldata, can call `createArt` with their own artist, receiver and mintFee for the same cred. Each call also overwrites `credMerkleRoot[credChainId][credId]`.

Attack path: 1. Cred creator submits createArt(signedData, sig, cfg). 2. An attacker copies signedData and sig and calls createArt with a config where artist and receiver are the attacker. 3. Each replay creates a new art in the cred's NFT contract, with rewards routed to the attacker.

Impact: Hijacking or spamming art creation for any cred with an unexpired signature. Arts and rewards go to the wrong artist, and the NFT contract is cluttered.

## [Medium] claim()/batchClaim() don't require msg.value >= mintFee and don't refund excess; fees paid from factory balance

File: PhiFactory.sol
Function: claim()/batchClaim()

`claim` computes `mintFee` and forwards `{value: mintFee}` to `this.merkleClaim` or `this.signatureClaim`, without checking `msg.value >= mintFee`. The forwarded value therefore comes from the factory's own balance if msg.value is smaller. Any excess `msg.value` is never refunded and stays in the factory. `batchClaim` only checks that `sum(ethValue_) == msg.value`, but each inner claim ignores `ethValue_[i]` as the amount it spends.

Attack path: 1. Users overpay in claim/batchClaim, so ETH accumulates in the factory. 2. An attacker calls claim (or batchClaim with zero ethValue_ entries) with msg.value 0 and a valid claim. 3. The inner call is funded from the factory's balance.

Impact: Overpayments are lost and can be taken by later claimers, or swept by the owner's `withdraw`. It also breaks the batch accounting.

## [Medium] createCred signature is replayable and creator_ is not bound to the signed data

File: Cred.sol
Function: createCred()

The signed payload has an unused uint256 slot, no nonce, and no used-signature tracking. The only checks are expiry, `sender == msg.sender` and a whitelisted curve. The sender can reuse the same signature to create unlimited creds before it expires. `creator_`, `buyShareRoyalty_` and `sellShareRoyalty_` are caller-supplied parameters outside the signature, so any address can be named creator of the cred. Each duplicate cred also gets the same merkle root and URL.

Attack path: 1. A user gets one signature for a cred URL and merkle root. 2. The user calls createCred repeatedly with different creator_ values and royalties. 3. Each call mints a new credId with the same verified metadata.

Impact: Duplicate or spoofed creds carry the 'verified' metadata. They can be given a royalty recipient of the attacker's choice, which undermines the signer's curation.

## [Medium] Zero-balance holders are never removed from shareBalance map, enabling unbounded growth and a gas-DoS of distribute()

File: Cred.sol
Function: _updateCuratorShareBalance()

On a sell to 0 the code calls `shareBalance[credId_].set(sender_, 0)` instead of `remove`. The address stays in the EnumerableMap forever, and `getCuratorAddresses` still iterates it. `CuratorRewardsDistributor.distribute` loops over all entries and makes two external `getShareNumber` calls per entry, plus a `depositBatch` over all of them. Entries can be added through `buyShareCredFor` to fresh addresses or through buy and sell cycles.

Attack path: 1. The attacker cycles shares through many addresses, buying and selling after the lock. 2. The map grows without bound. 3. `distribute(credId)` runs out of gas, so the accumulated `balanceOf[credId]` can never be paid out.

Impact: Curator rewards for a cred can be frozen permanently. The attack costs fees and gas per address, so it is practical only where the pool is large.
