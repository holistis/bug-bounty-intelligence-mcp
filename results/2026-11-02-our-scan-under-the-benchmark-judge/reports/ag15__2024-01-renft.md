# Audit report

## [High] Guard does not block setFallbackHandler; renter routes token calls via safe fallback to steal rentals

File: Guard.sol
Function: _checkTransaction()

Guard._checkTransaction only inspects ERC721/ERC1155 transfer and approve selectors, setApprovalForAll, safeBatchTransferFrom, setGuard, enableModule and disableModule. The Safe 1.4.1 function setFallbackHandler(address) (FallbackManager) is not blocked, and its only restriction is handler != address(this). Safe's fallback() forwards any unknown calldata with a CALL from the safe to the handler (msg.sender appended), so if the handler is set to the rented NFT contract, the NFT contract sees msg.sender == safe. Calls entering via the fallback never pass through checkTransaction, so the rental guard is completely bypassed.

Attack path: 1) Renter rents an ERC721 into their rental safe. 2) Renter executes a normal safe transaction calling safe.setFallbackHandler(nftContract); checkTransaction lets it through because the selector is not in the deny list. 3) Renter (or anyone) calls the safe address directly with calldata transferFrom(safe, attacker, tokenId); the safe fallback CALLs nftContract with that calldata, msg.sender is the safe, transfer succeeds. 4) Lender's stopRent later fails because the safe no longer owns the NFT.

Impact: Theft of every actively rented ERC721/ERC1155 and permanent loss for lenders; stopRent for the order reverts forever.

## [High] Renter adds malicious ERC20 tip to a BASE order so stopRent always reverts and NFT is never returned

File: Create.sol
Function: _rentFromZone() / _processBaseOrderConsideration()

Seaport lets the fulfiller append extra consideration items (tips) beyond totalOriginalConsiderationItems; these are part of orderParameters.consideration, which the modified ConsiderationEncoder._encodeValidateOrder copies into zoneParams.consideration. Create._processBaseOrderConsideration accepts any ERC20 consideration item and records it as an Item with SettleTo.LENDER, it is included in the rental order hash and ESCRW.increaseDeposit is called for it. Nothing restricts the token address to the lender's original consideration or to a token allowlist. On stop, PaymentEscrow._settlePayment calls _safeTransfer for every ERC20 item; a token that reverts on transfer from the escrow makes settlePayment, and therefore stopRent/stopRentBatch, revert permanently.

Attack path: 1) Lender lists a BASE order. 2) Renter deploys a token that transfers in normally but reverts when the escrow later sends it. 3) Renter fulfills the order with fulfillAdvancedOrder adding a tip consideration item of this token with recipient = PaymentEscrow; invariant checks pass since the ERC20 went to ESCRW. 4) After expiry, every stopRent call reverts inside ESCRW.settlePayment; the reclaim is rolled back.

Impact: Lender's rented NFT stays in the renter's safe forever (rental cannot be stopped, the renter keeps using it); the lender's ERC20 payment is also locked.

## [High] Guard checks prevModule instead of module in disableModule, allowing the Stop module to be removed

File: RentalConstants.sol
Function: Guard._checkTransaction() (gnosis_safe_disable_module_offset)

disableModule(address prevModule, address module) has prevModule at calldata byte 4 and module at byte 36. With data being a bytes memory, mload(data + 0x24) reads the first argument, so gnosis_safe_disable_module_offset = 0x24 makes the guard read prevModule, and _revertNonWhitelistedExtension is called on prevModule rather than on the module that is being disabled (the correct offset is 0x44). Safe enableModule inserts new modules at the head of the linked list, so after the renter enables any whitelisted extension E, the list is SENTINEL -> E -> Stop and disableModule(E, Stop) passes the guard.

Attack path: 1) Admin has whitelisted at least one extension E. 2) Renter enables E on their rental safe (allowed by the guard). 3) Renter executes disableModule(E, stopPolicy); guard loads E as the extension and it is whitelisted; Safe removes the Stop policy module. 4) Any stopRent then fails in execTransactionFromModule (GS104).

Impact: Rented assets can no longer be reclaimed by the protocol; lenders lose their NFTs permanently and payments stay in escrow.

## [Medium] Rental order hash omits rentalWallet, so an order can be stopped against a different protocol safe

File: Signer.sol
Function: _deriveRentalOrderHash()

_deriveRentalOrderHash encodes seaportOrderHash, items, hooks, orderType, lender, renter, startTimestamp and endTimestamp but not order.rentalWallet, although the RentalOrder type string declares it. Stop.stopRent uses the caller-supplied order.rentalWallet for the reclaim (execTransactionFromModule on that safe and Reclaimer check address(this)==rentalWallet) and for the rentedAssets ids passed to removeRentals, while the storage lookup only verifies the hash. Every protocol safe has the Stop module, so the reclaim runs on whatever safe is supplied, as long as it holds the same token/identifier and has enough rentedAssets for it.

Attack path: 1) Lender L rented ERC1155 id X (amount n) to safe A (order O1, expired). 2) Safe B holds an active rental of the same token id X with amount >= n from another lender M. 3) Anyone calls stopRent(O1 with rentalWallet = B). Hash matches, Stop reclaims n units from B to L, settles O1 payments and decrements rentedAssets[B,X]. 4) A's units remain locked forever (order deleted, rentedAssets[A,X] still set), and M's later stopRent fails because B no longer has the tokens.

Impact: Lender M loses rented ERC1155 tokens, M's rental can never be stopped, and the original assets in safe A are frozen.

## [Medium] EIP-712 hashes do not match declared types (metadata omits orderType/emittedExtraData)

File: Signer.sol
Function: _deriveOrderMetadataHash() / _deriveRentalTypehashes()

The OrderMetadata type string declares orderType, rentDuration, hooks and emittedExtraData, but _deriveOrderMetadataHash only encodes rentDuration and the hooks hash, so neither the lender's zoneHash nor the protocol-signed RentPayload commits to orderType or emittedExtraData. _RENTAL_ORDER_TYPEHASH is computed with abi.encode of the type strings (offsets and length words) instead of concatenation. The RentPayload typehash leaves out the referenced Hook type and does not sort referenced structs alphabetically, and _deriveRentalOrderHash leaves out rentalWallet. Hashes made with standard EIP-712 tools (wallet signTypedData, off-chain servers) will not match the on-chain hashes, and emittedExtraData can be changed freely by the fulfiller.

Attack path: 1) Lender signs a Seaport order whose zoneHash is computed off-chain per the declared OrderMetadata type. 2) On-chain _isValidOrderMetadata recomputes a different hash and the order cannot be fulfilled; or conversely integrators rely on the declared fields being signed while orderType/emittedExtraData are not covered, so a fulfiller can supply any emittedExtraData (and any orderType consistent with item layout) under the same zoneHash.

Impact: Breaks interoperability with EIP-712 signers and allows unsigned order metadata fields to be changed by the fulfiller.

## [Medium] Disabling a hook's onStop bit (or a reverting hook) permanently blocks stopping existing rentals

File: Stop.sol
Function: _removeHooks()

stopRent and stopRentBatch call _removeHooks before reclaiming whenever order.hooks is non-empty. _removeHooks reverts with Shared_DisabledHook if STORE.hookOnStop(target) is false and turns any revert inside IHook.onStop into a revert of the whole stop. The hook list is fixed in the stored order hash, so a rental cannot be stopped without calling those hooks. If the admin later changes the hook status bitmap (for example disables a buggy hook) or the hook starts reverting, every rental created with that hook can no longer be stopped.

Attack path: 1) Rental is created with hook H (onStart and onStop enabled). 2) GUARD_ADMIN calls updateHookStatus(H, bitmap without bit 4), or H reverts in onStop. 3) Lender calls stopRent after expiry; _removeHooks reverts and the reclaim never happens.

Impact: Rented NFTs stay in renter safes and escrowed ERC20 payments are locked for all affected orders.

## [Medium] Push-style settlement: a blacklisted or rejecting party makes stopRent revert and locks the NFT

File: PaymentEscrow.sol
Function: _settlePayment() / _safeTransfer()

Stop.stopRent performs reclaim, ESCRW.settlePayment and STORE.removeRentals atomically. _settlePayment pushes each ERC20 payment with _safeTransfer and reverts on any failure; Reclaimer uses safeTransferFrom to the lender, which reverts if the lender contract rejects the callback. If the renter or lender becomes blacklisted on a token such as USDC/USDT, or the token is paused, settlement reverts, so the NFT can never be reclaimed and all other payments in the order are frozen. In PAY orders a lender that cannot receive the NFT likewise stops the renter from ever being paid.

Attack path: 1) Rental uses USDC as payment. 2) The payment recipient (renter in a PAY order, lender in a BASE order) gets blacklisted or makes its contract reject ERC721/1155 receipt. 3) Any stopRent call reverts in _safeTransfer or safeTransferFrom.

Impact: The counterparty's NFT or payment is locked indefinitely; there is no alternative settlement path.

## [Medium] Identical partial fills create the same rental hash; second rental can never be stopped

File: Storage.sol
Function: addRentals()

Storage.addRentals sets orders[orderHash] = true without checking whether it is already true, while rentedAssets is incremented every time. The rental order hash depends on seaportOrderHash, items/amounts, hooks, orderType, lender, renter and timestamps; two partial fills of the same PARTIAL_RESTRICTED Seaport order with equal fill amounts by the same renter in the same block (e.g. two entries of the same order in fulfillAvailableAdvancedOrders) produce identical hashes. The RentPayload signature has no nonce and can be reused. The first stopRent deletes the order and decrements rentedAssets once; the second stop reverts with StorageModule_OrderDoesNotExist.

Attack path: 1) Lender lists an ERC1155 rental as a partially fillable restricted order. 2) Renter fills two equal fractions in one transaction/block with the same payload. 3) After expiry, stopRent works once; the second fraction's tokens stay in the safe with rentedAssets still non-zero, and its escrowed ERC20 stays counted in balanceOf.

Impact: Half of the lender's ERC1155 tokens and the matching escrowed payment are permanently locked.

## [Medium] Escrow assumes received amount equals item amount (fee-on-transfer/rebasing tokens break settlement)

File: PaymentEscrow.sol
Function: increaseDeposit() / _settlePayment() / skim()

Create calls ESCRW.increaseDeposit(item.token, item.amount) using the nominal Seaport amount, not the escrow's actual balance change. With fee-on-transfer or negatively rebasing tokens the escrow receives less than balanceOf records. _settlePayment later transfers the full item.amount, paying earlier stops with funds belonging to other rentals until the last stop reverts, and skim's trueBalance - syncedBalance underflows. Any ERC20 is accepted as payment, including renter-supplied tips.

Attack path: 1) Several rentals are paid in a fee-on-transfer token. 2) Early stops withdraw the full nominal amounts. 3) The last rental's stopRent reverts for lack of funds, so its NFT cannot be reclaimed; skim reverts too.

Impact: Insolvent escrow for that token, locked NFTs for later rentals, and blocked fee collection.

## [Medium] Anyone can front-run deployRentalSafe through the SafeProxyFactory to block a user's safe deployment

File: Factory.sol
Function: deployRentalSafe()

deployRentalSafe calls safeProxyFactory.createProxyWithNonce(singleton, initializer, keccak256(abi.encode(STORE.totalSafes() + 1, block.chainid))). The initializer and the salt nonce are fully predictable from the pending transaction and public state, and the SafeProxyFactory can be called by anyone. An attacker who submits the same createProxyWithNonce call first deploys the proxy at the CREATE2 address, so the Factory's call reverts. totalSafes does not change, so the victim's retry with the same owners/threshold collides again.

Attack path: 1) Victim sends deployRentalSafe(owners, threshold). 2) Attacker sees it in the mempool and calls safeProxyFactory.createProxyWithNonce with the identical initializer and nonce totalSafes+1. 3) Victim's transaction reverts; repeat for every retry.

Impact: Targeted users can be prevented from obtaining a registered rental safe, so they cannot rent (griefing at low cost).

## [Medium] Skipped orders in fulfillAvailable leave zeroed totalExecutions entries that make the zone revert

File: OrderCombiner.sol
Function: _performFinalChecksAndExecuteOrders() / _discoverUnspentOfferItems()

_discoverUnspentOfferItems counts every offer item with startAmount != 0 over all advancedOrders, including orders skipped with numerator = 0 (already filled, cancelled, or beyond maximumFulfilled), whose items keep their original startAmount. The fill loop that writes unspent items into totalExecutionItems skips those orders (continue on numerator == 0), so the array keeps trailing zero-initialised ReceivedItem entries (itemType 0 = NATIVE, recipient 0). Create._executionInvariantChecks reverts with CreatePolicy_SeaportItemTypeNotSupported on the NATIVE entry, so any fulfillAvailable batch containing a rental order and an unavailable order reverts instead of skipping it.

Attack path: 1) A user batches several rental orders with fulfillAvailableAdvancedOrders. 2) One order gets filled or cancelled first (or maximumFulfilled is lower than the batch). 3) The skipped order's unspent offer count adds empty entries; validateOrder for the remaining rental orders reverts and the whole batch fails.

Impact: Batch fulfillment of rentals breaks whenever any order in the batch is unavailable, which can also be caused deliberately by a lender cancelling or front-running.

## [Medium] Upgrading the Stop policy leaves existing safes with the old module, freezing all active rentals

File: Stop.sol
Function: stopRent() / Kernel._deactivatePolicy()

Each rental safe enables the specific Stop policy address as its module at deployment (Factory.initializeRentalSafe). Reclaiming needs Stop to be an enabled module on the safe and to hold the STORE.removeRentals and ESCRW.settlePayment permissions. When the old Stop policy is deactivated in favour of a new one, the old one loses its module permissions, and the new one is not a module on existing safes. Enabling the new module needs the renter to delegatecall a migration contract, which the renter has no reason to do.

Attack path: 1) Executor activates a new Stop policy and deactivates the old one. 2) Lenders call stopRent on the new policy: execTransactionFromModule fails (not a module); on the old policy: permissioned module calls revert. 3) Renters keep the assets.

Impact: All rentals open at upgrade time cannot be stopped until each renter migrates voluntarily.

## [Medium] Guard skips all rental checks when a hook path exists for the target contract

File: Guard.sol
Function: checkTransaction()

checkTransaction forwards to IHook.onTransaction and skips _checkTransaction completely when STORE.contractToHook(to) returns an active hook. The hook path is keyed only by the destination address, so if a hook is registered for an NFT contract (or for a contract that can move NFTs for the safe), none of the transfer/approval/module/guard restrictions apply to calls to it, and protection of rented items depends entirely on the hook.

Attack path: 1) GUARD_ADMIN connects a hook to contract T (e.g. a game contract that is also the ERC721). 2) Renter's safe calls T.transferFrom(safe, attacker, rentedId); guard forwards to the hook only and skips isRentedOut.

Impact: Rented assets of collections with a hook path can be transferred out if the hook does not copy the base checks.

## [High] Guard never blocks setFallbackHandler: rental safe can call the NFT as itself and bypass every guard check

File: Guard.sol
Function: checkTransaction() / _checkTransaction()

The Guard only inspects calls that go through Safe.execTransaction, and its denylist (transferFrom, safeTransferFrom x2, approve, setApprovalForAll, safeBatchTransferFrom, setGuard, enable/disableModule) has no entry for setFallbackHandler(address). A rental safe owner can therefore execute execTransaction(to = safe, data = setFallbackHandler(rentedNftContract)); the selector falls into the else-branch of _checkTransaction and passes. Safe's FallbackManager.fallback() then forwards any call whose selector the Safe does not implement (transferFrom, safeTransferFrom, approve, setApprovalForAll, ERC1155 safeTransferFrom) to the handler with call(), so the NFT contract sees msg.sender == rental safe, the token owner. Those fallback calls never reach Guard.checkTransaction, so isRentedOut is never consulted. The same unguarded handler also lets an ERC1155 rental be drained during creation: Seaport moves 1155s with safeTransferFrom, the safe's onERC1155Received is routed to the owner-chosen handler before validateOrder/addRentals has registered the rental, and a pre-signed owner execTransaction can move the tokens out while isRentedOut is still false.

Attack path: 1) Renter deploys a rental safe via Factory.deployRentalSafe and rents NFT X from lender L (any BASE order). 2) Renter runs execTransaction(to = safe, operation = Call, data = setFallbackHandler(NFT contract)); Guard passes it. 3) Anyone, including the renter's EOA, calls safe.transferFrom(safe, renter, X) (or safeTransferFrom/ERC1155 safeTransferFrom). The Safe fallback forwards the call to the NFT contract with the safe as msg.sender and the transfer succeeds. 4) At expiry stopRent reclaims nothing: _reclaimRentedItems fails because the safe no longer owns X, so StopPolicy_ReclaimFailed reverts; the rental can never be closed and the rent stays frozen in PaymentEscrow.

Impact: Complete loss of the lender's ERC721/ERC1155 for zero cost beyond the rent; breaks the stated main invariant that rented tokens cannot leave a rental wallet; the lender's payment is also permanently stuck in escrow because the order can never be stopped.

## [High] disableModule offset 0x24 makes the guard whitelist-check prevModule instead of module, so Stop can be disabled

File: Guard.sol
Function: _checkTransaction()

gnosis_safe_disable_module_offset is 0x24, the same value as for enableModule(address). For disableModule(address prevModule, address module) the first argument at 0x24 is prevModule; the module being removed sits at 0x44. The guard therefore calls _revertNonWhitelistedExtension(prevModule) and never checks the module that is actually disabled. Modules are inserted at the head of Safe's linked list, so when the renter enables any whitelisted extension E after setup the list is SENTINEL -> E -> Stop. The call disableModule(E, Stop) satisfies modules[E] == Stop in ModuleManager and passes the guard because E is whitelisted. The README lists 'rental safes can never call disableModule unless the target is whitelisted' as a main invariant, and this breaks it.

Attack path: 1) Admin has whitelisted at least one extension E (the whole whitelist feature presumes this). 2) Renter rents NFT X, then enables E on the safe (allowed, E is whitelisted). 3) Renter executes disableModule(prevModule = E, module = StopPolicy); the guard checks only E and lets it through. 4) Stop is no longer a module, so execTransactionFromModule from Stop reverts and _reclaimRentedItems always fails. 5) The guard still blocks transfers while rentedAssets is non-zero, so X is locked in the renter's safe forever and stopRent can never complete.

Impact: The lender permanently loses the rented asset (renter keeps in-wallet use of it indefinitely) and the rent payment is stuck in PaymentEscrow; only requires one whitelisted extension to exist.

## [High] Seaport tip items let the renter inject an attacker ERC20 payment item that makes stopRent revert forever

File: Create.sol
Function: _processBaseOrderConsideration()

Seaport only hashes the first totalOriginalConsiderationItems consideration items; the fulfiller may append extra consideration items (tips) and the vendored OrderValidator/Assertions only require consideration.length >= original. The zone receives these extras in zoneParams.consideration. _processBaseOrderConsideration turns every ERC20 consideration entry into an Item with settleTo LENDER, and _executionInvariantChecks only requires that ERC20 executions go to the escrow, so a tip ERC20 with recipient = PaymentEscrow is accepted and ESCRW.increaseDeposit is called for it. The RentalOrder hash and stored order now contain this item. At stop, PaymentEscrow._settlePayment loops over all ERC20 items and calls _safeTransfer(token, lender, amount) for the tip token; if that token is attacker-controlled and reverts or returns false, the whole stopRent transaction (reclaim included) reverts. The server signature (RentPayload) does not cover the consideration, so nothing off-chain filters this.

Attack path: 1) Renter deploys malicious ERC20 M with a toggle that makes transfer revert. 2) Renter calls fulfillAdvancedOrder on a lender's BASE order with an extra consideration item {ERC20, M, amount 1, recipient = PaymentEscrow}; Seaport accepts the tip and the zone validates it. 3) Rental starts normally; the escrow records a deposit of M. 4) After expiry anyone calls stopRent/stopRentBatch; _settlePayment reaches the M item, M.transfer reverts, the transaction reverts and the NFT is never reclaimed. 5) Renter flips M to revert and keeps using the NFT in the safe indefinitely.

Impact: Permanent lock of the lender's NFT in the renter's safe and permanent lock of the real rent in escrow; also usable to bloat the items array until stop exceeds the block gas limit.

## [Medium] Identical partial fills in one block collide on the rental order hash and double-count rentedAssets and escrow

File: Create.sol
Function: _rentFromZone()

Nothing in Create or in the vendored Seaport rejects PARTIAL_RESTRICTED orders, and ZoneParameters carries the fractional offer amounts. The rental order hash is built from seaportOrderHash, items, hooks, orderType, lender, renter, startTimestamp and endTimestamp. Two equal partial fills of the same order (same renter and safe, same block timestamp) therefore produce the same hash. Storage.addRentals just sets orders[hash] = true (a bool, no existence check) and adds the amounts to rentedAssets each time, and ESCRW.increaseDeposit is called twice. Stopping removes the single order record once and subtracts the amount once.

Attack path: 1) Lender signs a PARTIAL_RESTRICTED ERC1155 + ERC20 order with the rental zone. 2) Renter fulfils two equal fractions in the same transaction/block into the same safe (e.g. fulfillAvailableAdvancedOrders with the same order twice). 3) Both validateOrder calls derive the same orderHash; rentedAssets[(safe, token, id)] = 2a, escrow balanceOf = 2p, one order record. 4) stopRent(order) reclaims a tokens, pays out p, deletes the order and decrements rentedAssets to a. 5) A second stop reverts with OrderDoesNotExist, so a tokens stay in the safe behind the guard forever and p stays in the escrow.

Impact: The lender loses the second fraction of the 1155 tokens permanently while the renter keeps in-wallet use of them; the second payment is unrecoverable (not skimmable because it is counted as synced).

## [Medium] Protocol signature over RentPayload is not bound to the Seaport order, so one signature can be replayed on any order with matching metadata

File: Create.sol
Function: validateOrder()

The CREATE_SIGNER signature covers only (fulfillment.recipient, metadata hash = rentDuration + hooks, expiration, intendedFulfiller). It does not include the Seaport order hash, offerer, items or any nonce, and the lender's zoneHash only commits to the same metadata hash. Any fulfiller holding one valid signed payload can present it again, unchanged, with a different order (different lender, collection, price) whose zoneHash equals the same metadata hash, as often as they like until the expiration. The protocol signer's approval is therefore not an approval of a specific rental.

Attack path: 1) Renter obtains one signed payload for duration D, no hooks, recipient S, expiration T. 2) Within T, renter fulfils many unrelated lender orders that all use zoneHash = hash(D, no hooks), each time passing the same payload and signature. 3) Each validateOrder passes the expiry, fulfiller and signer checks and creates a rental.

Impact: Any off-chain gating the signer is meant to enforce per order (eligibility, order screening, rate limits) can be bypassed for unlimited orders within one signature lifetime.

## [Medium] Unavailable orders leave zeroed NATIVE entries in totalExecutions, so any batch with an unavailable order reverts in the zone

File: OrderCombiner.sol
Function: _discoverUnspentOfferItems() / _performFinalChecksAndExecuteOrders()

The modified Seaport sizes totalExecutionItems as executions.length + _discoverUnspentOfferItems(advancedOrders). That helper counts every offer item with startAmount != 0 for all orders, including orders with numerator == 0 (unavailable, skipped), whose offer amounts were never fractioned or consumed. Only offer items of available orders are written into the array afterwards, so the trailing entries stay zero-initialised (itemType NATIVE, token 0, recipient 0). Create._executionInvariantChecks loops over all totalExecutions and reverts with CreatePolicy_SeaportItemTypeNotSupported for an entry that is neither ERC20 nor ERC721/1155. Every rental order's validateOrder in that call therefore reverts.

Attack path: 1) Renter submits fulfillAvailableAdvancedOrders with N rental orders. 2) One order is front-run (filled/cancelled/expired) so it is unavailable. 3) The remaining orders execute their transfers, then validateOrder reverts on the zeroed execution, so the whole call reverts instead of fulfilling the available orders.

Impact: The 'available' batch semantics are broken for rentals and any user can grief batch rentals by consuming one order in the batch.

## [Medium] Order metadata hash omits orderType and emittedExtraData, so the lender's zoneHash does not commit to them

File: Signer.sol
Function: _deriveOrderMetadataHash()

The type string is 'OrderMetadata(uint8 orderType,uint256 rentDuration,Hook[] hooks,bytes emittedExtraData)' and the docs say the zoneHash binds all of it, but the hash is abi.encode(typehash, rentDuration, keccak256(hookHashes)) only. The fulfiller supplies RentPayload.metadata, so orderType and emittedExtraData are fully controlled by the fulfiller and covered by neither the Seaport signature (zoneHash) nor the protocol signature. orderType is later stored in the rental order and decides stop rules and settlement (BASE stoppable only at expiry, PAY by the lender at any time, pro-rata vs full payout), and emittedExtraData goes straight into the RentalOrderStarted event. The typehash derivations are also non-standard (abi.encode of type strings for the rental order, RentPayload type string without the Hook dependency and in non-EIP-712 order), so standard typed-data signers will not reproduce them.

Attack path: A fulfiller passes the lender's order with any emittedExtraData of their choice (event spoofing for off-chain indexers) and, where an order shape satisfies two order types' item rules, picks the orderType that is stored. Off-chain consumers trusting the event or the order type take attacker-chosen data as lender-signed.

Impact: Lender-signed terms are not enforced on-chain for orderType/emittedExtraData; event data can be forged; settlement rules may be selected by the fulfiller.

## [Medium] Reclaim and payment settlement are atomic push transfers, so one failing transfer blocks returning the NFT

File: PaymentEscrow.sol
Function: _settlePayment() / _safeTransfer()

stopRent runs hooks, reclaim of the NFTs and ESCRW.settlePayment in one transaction, and settlePayment pushes tokens to the lender and renter with _safeTransfer, reverting on any failure. A transfer that reverts for the recipient (USDC/USDT blacklist, ERC777-style receiver hook on a Seaport-supported token, pausable token, or a zero-value transfer on tokens that reject zero amounts when renterAmount or lenderAmount rounds to 0 in _calculatePaymentProRata) therefore also rolls back the reclaim. For PAY orders the payment recipient is the renter, who controls whether a hook-based token transfer to them reverts.

Attack path: 1) Lender lists a PAY order paying a token whose transfer can fail for the renter (blacklistable or hook-based). 2) Renter rents through a contract wallet owner or becomes blocked, so _safeTransfer(token, renter, amount) reverts. 3) stopRent by the lender or anyone after expiry reverts at settlePayment, the NFT stays in the renter's safe and the lender's payment stays in escrow.

Impact: Lender's NFT and escrowed payment can be held hostage by whoever controls a payment recipient or by token admin actions; depends on token choice.

## [Medium] rentalWallet is not part of the rental order hash, so stopRent accepts an attacker-chosen wallet for the same stored order

File: Signer.sol
Function: _deriveRentalOrderHash()

The RentalOrder type string lists rentalWallet but abi.encode in _deriveRentalOrderHash leaves it out, so STORE.orders[hash] authenticates everything except the wallet. stopRent builds rentalAssetUpdates from order.rentalWallet, calls ISafe(order.rentalWallet).execTransactionFromModule and then STORE.removeRentals with ids derived from that same unauthenticated wallet. A caller can thus stop a stored order while pointing the reclaim and the rentedAssets decrement at a different protocol safe. For ERC721 the decrement usually underflows and reverts, but for ERC1155 ids rented to two safes the reclaim can pull tokens out of the second safe and release its guard accounting, while the first safe keeps tokens with an undecremented rentedAssets.

Attack path: 1) Two ERC1155 rentals of the same token id exist: order A in safe W1 and order B in safe W2 (rentedAssets[(W2,token,id)] >= amount A). 2) After A expires the caller submits stopRent with order A but rentalWallet = W2. 3) The hash matches, tokens are reclaimed from W2 to A's lender, rentedAssets for W2 is decremented, and order A is deleted. 4) The tokens in W1 remain locked behind rentedAssets forever and order B can no longer be reclaimed from W2.

Impact: Cross-rental accounting corruption: another lender's tokens in W2 are handed to A's lender, W1's tokens become unrecoverable, and order B's payment is frozen.

## [Medium] stopRent reverts when a referenced hook no longer has the stop bit set, locking rentals started with that hook

File: Stop.sol
Function: _removeHooks()

Create._addHooks only requires STORE.hookOnStart(target) while Stop._removeHooks requires STORE.hookOnStop(target) and reverts with Shared_DisabledHook otherwise. Hook status is an admin-mutable bitmap (any value 0..7). A hook enabled with start only (bitmap 2 or 3), or whose stop bit or status is later cleared with updateHookStatus, makes every existing rental that references it impossible to stop, since the hook check runs before the reclaim in the same transaction. A hook whose onStop reverts has the same effect.

Attack path: 1) Hook H is set to bitmap 3 (transaction + start) or later reset to 0. 2) Lender and renter create rentals that list H. 3) stopRent/stopRentBatch reverts in _removeHooks, so reclaim and payment settlement never run.

Impact: NFTs and escrowed payments of all rentals using that hook are frozen until admin re-enables the stop bit; a configuration mistake or hook revert becomes a permanent lock.

## [Medium] Rental safe deployment can be front-run by pre-creating the same Safe through SafeProxyFactory

File: Factory.sol
Function: deployRentalSafe()

The salt nonce is uint256(keccak256(abi.encode(STORE.totalSafes() + 1, block.chainid))) and the initializer depends only on public inputs (owners, threshold, factory, stop and guard addresses, handler). Anyone can call safeProxyFactory.createProxyWithNonce(safeSingleton, sameInitializer, sameNonce) directly before the victim's transaction, which deploys the Safe at the victim's intended address without registering it in Storage. The victim's deployRentalSafe then fails on the create2 collision. totalSafes only increments on a successful registration, so the retry computes the same nonce and fails again for that owner/threshold combination.

Attack path: 1) Attacker watches a pending deployRentalSafe(owners, threshold). 2) Attacker calls SafeProxyFactory.createProxyWithNonce with the identical initializer and nonce first. 3) Victim's call reverts and every retry with the same parameters keeps reverting until another user's deployment bumps totalSafes.

Impact: Targeted griefing of safe creation for chosen owner sets; the unregistered look-alike safe cannot be used for rentals (deployedSafes == 0).
