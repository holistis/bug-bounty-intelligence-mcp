Operator can induce denial‑of‑service by registering inactive supply slots

Model confidence: 92%

File: src/core/MonetrixAccountant.sol

Function: addMultisigSupplyToken(uint64)

Category: LIVENESS

The `addMultisigSupplyToken` function allows an operator to register any whitelisted spot token without verifying that the corresponding 0x811 slot is actually activated on Hypercore. The registered token is later read in `_readL1Backing`, where `PrecompileReader.suppliedNotionalUsdcFromPerp` is called. If the slot is not activated, the pre‑compile reverts, causing `totalBackingSigned()` (and any function that depends on it, e.g., `settleDailyPnL`) to revert, effectively halting yield settlement and other accounting‑dependent operations.

Attack path: 1. Attacker obtains the Operator role (or compromises an operator key).

Impact: Yield settlement and any accounting‑dependent functions become permanently blocked, leading to loss of expected rewards and possible loss of confidence; the protocol can be effectively frozen until the bogus entry is removed (requires operator action) or a governance upgrade.

Recommendation: Validate that a supplied slot is active before registering it (e.g., query the pre‑compile for activation status) or catch and ignore revert errors when reading inactive slots. Alternatively, restrict registration to tokens that have a non‑zero supplied balance.

Medium

State update before external escrow call in claimUnstake leads to potential asset loss

Model confidence: 85%

File: src/tokens/sUSDM.sol

Function: claimUnstake(uint256)

Category: ORDERING

The function deletes the unstake request and updates `totalPendingClaims` before invoking `escrow.release`, which is an external call to another contract. If `escrow.release` fails (e.g., reverts after state changes or returns false without reverting), the user's claim is erased while the USDM remains locked in the escrow, breaking accounting and potentially causing loss of funds.

Attack path: 1. Attacker (any user) creates an unstake request via `cooldownShares` or `cooldownAssets`.

Impact: Users can permanently lose access to their USDM and the protocol’s accounting (`totalPendingClaims`) becomes inconsistent, potentially affecting solvency checks and overall protocol health.

Recommendation: Follow the checks‑effects‑interactions pattern: perform the external `escrow.release` call before mutating contract state, or ensure `escrow.release` reverts on any failure and wrap the call in a try/catch that restores state on error.
