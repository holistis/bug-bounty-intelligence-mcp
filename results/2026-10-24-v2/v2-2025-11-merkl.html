Reentrancy via external ETH transfer in NativeTokenWrapper before token balance update

Model confidence: 95%

File: contracts/partners/tokenWrappers/NativeTokenWrapper.sol

Function: _beforeTokenTransfer()

Category: ORDERING

The `_beforeTokenTransfer` hook sends ETH to the `to` address (or `feeRecipient`) using a low‑level call before the ERC20 balances are updated. This external call allows a malicious recipient contract to re‑enter the token contract (e.g., call `transfer` again) while the sender’s balance is still unchanged, enabling double‑spending of tokens and draining ETH from the wrapper.

Attack path: 1. Attacker deploys a contract with a payable fallback that calls `NativeTokenWrapper.transfer(address,uint256)` back into the token.

Impact: Unlimited extraction of ETH held by the wrapper and arbitrary duplication of token balances, leading to loss of funds and potential protocol insolvency.

Recommendation: Move the ETH transfer to `_afterTokenTransfer` after balances are updated, or protect the external call with a re‑entrancy guard (e.g., OpenZeppelin’s `nonReentrant`). Follow the checks‑effects‑interactions pattern to avoid external calls before state changes.

Medium

Missing re‑entrancy protection on `increaseTokenBalance`

Model confidence: 85%

File: contracts/DistributionCreator.sol

Function: increaseTokenBalance(address,address,uint256)

Category: ORDERING

The function pulls tokens from `msg.sender` via `IERC20.safeTransferFrom` and **updates internal accounting only after the external call**. No `nonReentrant` guard is applied, so a malicious ERC‑777 (or any token that executes a callback on `transferFrom`) can re‑enter the contract before the balance is updated.

Attack path: 1. Attacker deploys a malicious ERC‑20 token that calls back into `increaseTokenBalance` during `transferFrom`.

Impact: Inconsistent accounting could be leveraged to inflate a user’s recorded balance, enabling later unauthorized withdrawals or causing the contract to think it holds more tokens than it actually does, leading to solvency issues.

Recommendation: Add the `nonReentrant` modifier (from `ReentrancyGuardUpgradeable`) to `increaseTokenBalance` and any other external‑call‑heavy functions, or move the balance update before the external token transfer.

Missing re‑entrancy protection on `decreaseTokenBalance`

File: contracts/DistributionCreator.sol

Function: decreaseTokenBalance(address,address,address,uint256)

Category: ORDERING

The function updates the internal `creatorBalance` mapping **before** transferring tokens out with `IERC20.safeTransfer`. Although the transfer occurs after the state change, `safeTransfer` supports ERC‑777 tokens that can execute arbitrary code on receipt, allowing a re‑entrancy attack back into the contract.

Attack path: 1. Attacker creates a malicious ERC‑20 token that calls back into `decreaseTokenBalance` (or another state‑changing function) during `safeTransfer`.

Impact: The attacker can manipulate allowances or balances to later withdraw more tokens than intended, compromising the protocol’s solvency.

Recommendation: Protect `decreaseTokenBalance` with the `nonReentrant` modifier, or transfer tokens **before** updating internal balances and use a checks‑effects‑interactions pattern.
