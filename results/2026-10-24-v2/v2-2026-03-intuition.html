Medium

Inaccurate block-to-timestamp estimation in totalSupplyAt enables governance manipulation

Model confidence: 65%

File: src/external/curve/VotingEscrow.sol

Function: totalSupplyAt()

Category: SETTLEMENT

The `totalSupplyAt` function estimates a historical timestamp for a given block number using linear interpolation between checkpoints. When `point.blk == point_next.blk` (consecutive checkpoints in the same block) or `point.blk == block.number` (latest checkpoint), the division is skipped and `dt` remains 0, causing the function to return the supply at the exact checkpoint timestamp rather than the interpolated time. This systematic underestimation of elapsed time inflates the calculated total voting power for periods immediately after checkpoints.

Attack path: 1. Attacker identifies a period where a new global checkpoint was created (e.g., after a large lock creation). 2. Attacker calls `totalSupplyAt` with a block number shortly after that checkpoint's block. 3. Due to the `dt = 0` fallback, the returned supply is higher than the true time-decayed supply. 4. If this value is used on-chain for quorum thresholds or proposal validation (e.g., via an external governor reading `totalSupplyAt`), the attacker can make proposals appear to meet quorum when they do not, or bypass minimum-voting-power requirements.

Impact: Governance decisions (quorum, vote thresholds) based on `totalSupplyAt` can be manipulated to pass illegitimate proposals or block legitimate ones, leading to protocol misgovernance.

Recommendation: When `point.blk == point_next.blk`, fall back to using `block.timestamp - point.ts` (or the next checkpoint's timestamp) for `dt` instead of leaving it at 0. Add a comment documenting the interpolation assumption.

Unbounded loop in _supply_at allows gas griefing via totalSupplyAtT

Model confidence: 55%

File: src/external/curve/VotingEscrow.sol

Function: _supply_at()

Category: LIVENESS

The `_supply_at` internal function iterates up to 255 times (weekly steps) to compute total supply at a target timestamp `t`. While the loop is bounded, an attacker can call the public `totalSupplyAtT(t)` with a `t` value far in the future (e.g., `type(uint256).max`), forcing the loop to execute all 255 iterations and consume ~200k+ gas. Although view functions cannot halt the protocol, they can be used to grief off-chain indexers, simulation tools, or gas-estimation APIs that call this function during transaction simulation.

Attack path: 1. Attacker calls `totalSupplyAtT(type(uint256).max)` via `eth_call` or a contract that relays the call. 2. The EVM executes 255 loop iterations with slope-change lookups. 3. Repeated calls degrade RPC performance or cause gas-estimation failures for downstream integrators.

Impact: Degraded off-chain tooling reliability; potential DoS for front-ends that simulate governance actions using this view.

Recommendation: Cap the maximum timestamp accepted by `totalSupplyAtT` to `block.timestamp + MAX_FUTURE_LOOKAHEAD` (e.g., 4 years) and revert for larger values.

Low

Precision loss in balanceOfAt block-time interpolation skews user voting power

Model confidence: 50%

File: src/external/curve/VotingEscrow.sol

Function: balanceOfAt()

Category: ACCOUNTING

The `balanceOfAt` function estimates the block timestamp for a historical block using `dt = (d_t * (_block - point_0.blk)) / d_block`. When `d_block` is large, integer division truncates the fractional progress, causing `block_time` to be slightly earlier than the true timestamp. This results in a marginally higher calculated voting power (since less decay is applied). The bias is small per call but systematic and favors the caller.

Attack path: 1. Attacker queries `balanceOfAt(addr, historical_block)` for a block far from the nearest checkpoint. 2. The truncated `block_time` yields a voting power slightly above the true value. 3. If this value is used on-chain (e.g., for a snapshot-based vote or a contract that checks `balanceOfAt` for eligibility), the attacker gains a small but repeatable advantage.

Impact: Minor inflation of historical voting power; could affect close snapshot votes or eligibility checks that rely on precise historical balances.

Recommendation: Use a rounding-up division for `dt` when calculating `block_time` (e.g., `(d_t * (_block - point_0.blk) + d_block - 1) / d_block`) to avoid systematic underestimation of elapsed time.
