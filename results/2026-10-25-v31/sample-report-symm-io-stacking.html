notifyRewardAmount lacks REWARD_MANAGER_ROLE check

Model confidence: 95%

File: SymmStaking.sol

Function: notifyRewardAmount()

Category: Missing access control

The function is declared `external nonReentrant whenNotPaused` with no role modifier, so any untrusted caller can invoke it. It pulls `amount` of any whitelisted reward token from `msg.sender` and calls `_addRewardsForToken`, which recomputes `state.rate` and `state.periodFinish`. Because the caller supplies the tokens, they can manipulate the reward rate/duration for all stakers.

Attack path: 1) Attacker acquires a tiny amount of a whitelisted reward token. 2) Calls `notifyRewardAmount([token],[1])` repeatedly, or with a large amount they own, to overwrite `state.rate` and `state.periodFinish`. 3) By notifying right before others claim, they reset `lastUpdated`/`periodFinish` and dilute or extend the reward schedule; combined with `_updateRewardsStates(address(0))` they can also force global state updates at chosen times.

Impact: Reward accounting for all stakers can be manipulated (rate dilution, schedule extension), causing incorrect reward distribution and potential loss of rewards for honest stakers.

Recommendation: Add `onlyRole(REWARD_MANAGER_ROLE)` to `notifyRewardAmount`.

initialize is callable by anyone on uninitialized proxy

Model confidence: 85%

File: SymmStaking.sol

Function: initialize()

Category: Initializer front-running

`initialize` is `external initializer` with no access restriction. If the proxy is deployed and not initialized in the same transaction, any untrusted actor can call it first and become `admin`, receiving DEFAULT_ADMIN_ROLE, REWARD_MANAGER_ROLE, PAUSER_ROLE, and UNPAUSER_ROLE. The same pattern exists in `SymmVesting.initialize` and `Vesting.__vesting_init`.

Attack path: 1) Observe proxy deployment. 2) Front-run the intended `initialize` call with attacker-controlled `admin` and `_stakingToken`. 3) Attacker now holds all roles and can pause, configure reward tokens, rescue funds, and set vesting plans.

Impact: Full takeover of the staking/vesting contract; theft of funds via `rescueTokens`, arbitrary reward configuration, and denial of service.

Recommendation: Use `initializer` plus an `onlyInitializing`-style guard or initialize atomically in the deployment script; consider `_disableInitializers()` in the implementation constructor.

High

SymmStaking reward rate truncation causes stuck pendingRewards

Model confidence: 85%

File: SymmStaking.sol

Function: _addRewardsForToken()

Category: Rounding / Accounting drift

When a new reward amount is notified, `state.rate = amount / state.duration` (or `(amount + leftover) / state.duration`) truncates the remainder. The full `amount` is added to `pendingRewards[token]`, but the sum of `rate * duration` over the period is less than `amount`. The truncated dust is never claimable, so `pendingRewards[token]` can never reach zero, permanently blocking `configureRewardToken(token, false)` (which reverts if `pendingRewards[token] > 10`) and leaving tokens stranded.

Attack path: 1) Attacker (any reward manager is trusted, but the truncation is triggered by any notify) — actually the flaw is triggered by any legitimate notifyRewardAmount call. 2) Notify an amount not divisible by duration (e.g., 1 week = 604800, amount = 604801). 3) rate = 1, so only 604800 is distributed; 1 wei remains in pendingRewards forever. 4) Repeat to accumulate >10 wei of dust. 5) Admin can no longer delist the token; the dust is permanently locked.

Impact: Permanent accounting drift between `pendingRewards` and actual distributable rewards; reward tokens can never be delisted; dust funds locked.

Recommendation: Track the undistributed remainder and add it to the next notify, or compute rate as `amount * 1e18 / duration` and store per-token precision, or subtract the actual distributed amount from pendingRewards.

Spot pool balances used for liquidity quote enables sandwich manipulation

Model confidence: 80%

File: SymmVesting.sol

Function: getLiquidityQuote()

Category: Spot-price manipulation

`getLiquidityQuote` derives `usdcAmount` and `lpAmount` directly from `POOL.getCurrentLiveBalances()` and `POOL.totalSupply()`, which are instantaneous spot balances. An attacker can flash-loan and swap against the pool to skew the SYMM/USDC ratio right before a victim's `addLiquidity`/`addLiquidityByPercentage` call, forcing the victim to contribute far more USDC (or receive far fewer LP tokens) than fair. The `maxUsdcIn`/`minLpAmount` guards only help if the victim sets them tightly; the default 1% slippage path uses the manipulated `expectedLpAmount` as its own baseline, so it provides no real protection.

Attack path: 1) Attacker flash-borrows USDC and swaps heavily into the pool to depress SYMM price / inflate USDC per SYMM. 2) Victim calls `addLiquidity` (or `addLiquidityByPercentage`) with default or loose slippage; `getLiquidityQuote` returns inflated `usdcIn` and deflated `lpAmount`. 3) Victim's USDC is pulled and LP minted at the skewed ratio. 4) Attacker reverses the swap, pocketing the difference; victim's LP is worth less than intended.

Impact: Direct loss of user USDC and/or LP value on every liquidity addition; repeatable value extraction from vesting users.

Recommendation: Use a TWAP or oracle-based price for the quote, or require the caller to supply an explicit `minLpAmount`/`maxUsdcIn` and reject the default path; compute slippage against a manipulation-resistant reference.

Rescue of staking token enables theft of staked user funds

Model confidence: 75%

File: SymmStaking.sol

Function: rescueTokens()

Category: Unrecoverable/Stuck-Funds / Admin-drain of user collateral

rescueTokens() lets DEFAULT_ADMIN_ROLE transfer any token, including the staking token, out of the contract with no restriction. The staking token is the sole collateral backing balanceOf/totalSupply, so once withdrawn, users' withdraw() calls revert on insufficient balance (withdrawals become permanently frozen). This is a liveness/DoS trap: a legitimate withdrawal path is broken by an arbitrary rescue of the collateral asset.

Attack path: 1) Admin (or compromised admin key) calls rescueTokens(stakingToken, fullBalance, attacker). 2) All staked SYMM is transferred out of the contract. 3) Every user's withdraw() reverts with insufficient-balance because the contract no longer holds the tokens. 4) Users cannot exit; their staked balances are permanently stuck on-chain.

Impact: Permanent freezing of all user withdrawals; total loss of staked principal from the contract's perspective (users hold only accounting balances, no backing tokens).

Recommendation: Disallow rescuing the staking token and reward tokens with pending obligations, or restrict rescue to explicitly tracked surplus (contract balance minus totalSupply minus pendingRewards).

Medium

SymmAllocationClaimer claim() truncates amountToClaim, inflating adminClaimableAmount

Model confidence: 70%

File: SymmAllocationClaimer.sol

Function: claim()

Category: Rounding / Accounting

`amountToClaim = (userAllocations[msg.sender] * mintFactor) / 1e18` truncates down. The remainder `userAllocations[msg.sender] - amountToClaim` is added to `adminClaimableAmount`. Since `mintFactor <= 1e18`, the remainder is non-negative and represents the portion of the user's allocation that goes to the foundation. However, `userAllocations[msg.sender]` is set to 0 after claiming, so the user cannot claim the remainder. This is intended (the remainder is the foundation's cut), but the truncation means the foundation receives slightly more than `allocation * (1 - mintFactor)`, and `totalMintAmount` may not equal `totalUserClaimedAmount + adminClaimedAmount` exactly. More importantly, if `mintFactor` is very small (e.g., 1), `amountToClaim` can be 0 for small allocations, and the user receives nothing while their entire allocation is credited to the foundation.

Attack path: 1) User with a small allocation (e.g., 1 wei) calls `claim()`. 2) `amountToClaim = (1 * mintFactor) / 1e18 = 0`. 3) `adminClaimableAmount += 1`. 4) User receives 0 tokens; foundation can claim 1 wei. 5) User's allocation is zeroed, so they cannot retry.

Impact: Users with small allocations receive nothing; foundation receives their entire allocation; `totalUserClaimedAmount` under-reports actual user receipts.

Recommendation: Revert if `amountToClaim == 0`, or round in favor of the user, or document that dust goes to the foundation.

High

Permit2 approvals use block.timestamp as expiration, causing immediate expiry

Model confidence: 70%

File: SymmVesting.sol

Function: _addLiquidity()

Category: Signature/Permit

The contract calls `PERMIT2.approve(SYMM, address(ROUTER), uint160(symmIn), uint48(block.timestamp))` and the same for USDC, setting the Permit2 allowance expiration to the current block timestamp. Permit2 treats an allowance as valid only while `block.timestamp <= expiration`, so the approval is effectively already expired (or expires within the same block) by the time the router pulls the tokens. This makes the subsequent `ROUTER.addLiquidityProportional` call fail to transfer tokens, breaking the entire addLiquidity flow.

Attack path: 1. Any user calls `addLiquidity` or `addLiquidityByPercentage`. 2. The contract approves Permit2 with expiration = block.timestamp. 3. The router's Permit2 transferFrom sees expiration <= block.timestamp and reverts. 4. The user's USDC has already been pulled into the contract, and the transaction reverts, but the flow is permanently broken for all users.

Impact: addLiquidity is unusable; users cannot convert vesting SYMM into LP. If the router tolerates the boundary, approvals are effectively single-block, enabling griefing/race conditions on allowance reuse.

Recommendation: Set expiration to `block.timestamp + someBuffer` (e.g., 30 minutes) or use `type(uint48).max` if the router consumes the allowance atomically.

High

Reward rate dilution lets late stakers capture disproportionate share

Model confidence: 70%

File: SymmStaking.sol

Function: notifyRewardAmount()

Category: Reward accounting / incentive flaw

When notifyRewardAmount is called while a reward period is still active, the leftover is computed as `remaining * state.rate` and the new rate is `(amount + leftover) / state.duration`, but `state.lastUpdated` is set to `block.timestamp` and `periodFinish` is extended by a full `duration`. Because `_updateRewardsStates(address(0))` is called first, the perTokenStored is snapshotted at the old rate, but the new rate is applied over the entire new duration including the already-elapsed portion, so the effective emission rate for the remaining window is inflated/deflated inconsistently with the leftover accounting. An attacker can time a large deposit right before a notifyRewardAmount call to capture rewards computed at the boosted rate for time they did not stake.

Attack path: 1) Attacker observes pending notifyRewardAmount (or front-runs it). 2) Attacker deposits a large amount just before the call so balanceOf is huge at the snapshot. 3) notifyRewardAmount sets a new rate over the full duration while lastUpdated = now, so the attacker's large balance accrues rewards at the new rate for the entire new period. 4) Attacker withdraws after accruing, capturing a share of rewards disproportionate to actual staking time.

Impact: Unfair reward distribution; honest long-term stakers receive less than entitled; reward pool can be drained faster than intended.

Recommendation: Compute the new rate using only the remaining duration for the leftover and set periodFinish = block.timestamp + remaining (or use the standard Synthetix pattern where rate = (amount + leftover) / duration and lastUpdated is set before recomputing perTokenStored).

SymmVesting addLiquidityByPercentage uses 1e18 divisor on locked amount

Model confidence: 65%

File: SymmVesting.sol

Function: addLiquidityByPercentage()

Category: Precision / Percentage math

`amount = (getLockedAmountsForToken(msg.sender, SYMM) * percentage) / 1e18`. If `percentage` is intended as a fraction of 1e18 (i.e., 1e18 = 100%), this is correct, but the docstring in `claimLockedTokenByPercentage` says "between 0 and 1 -- 1 for 100%", implying `percentage` should be scaled by 1e18. If a user passes `1` expecting 100%, they get 1 wei of SYMM used, and the rest of the locked amount is untouched — but if they pass `1e18` expecting 100%, it works. The ambiguity plus truncation means a user passing a small percentage gets `amount = 0`, then `_addLiquidityProcess` reverts on `symmLockedAmount < amount` only if locked < 0 (never), so it proceeds with `amount = 0`, calling `_addLiquidity(0, ...)` which computes `usdcIn = 0`, `lpAmount = 0`, and then `resetAmount(symmLockedAmount - 0)` — resetting the vesting plan's start time to now without adding liquidity, effectively extending the vesting schedule for free.

Attack path: 1) User calls `addLiquidityByPercentage(0, 0, 0)` or a tiny percentage that truncates to 0. 2) `_addLiquidityProcess` proceeds with `amount = 0`. 3) `_addLiquidity(0, ...)` returns `amountsIn = [0,0]`, `lpAmount = 0`. 4) `symmVestingPlan.resetAmount(symmLockedAmount - 0)` rebases the vesting plan from `block.timestamp`, extending the end time by the remaining duration. 5) User repeats to perpetually extend vesting (or grief themselves, but also affects `totalVested` accounting).

Impact: Vesting schedule can be silently rebased/extended; `totalVested` accounting may drift; zero-amount liquidity operations pollute state.

Recommendation: Revert if `amount == 0` in `_addLiquidityProcess`, and document/clarify the percentage scale.

High

pendingRewards underflow on claim after token de-whitelist

Model confidence: 65%

File: SymmStaking.sol

Function: _claimRewardsFor()

Category: Accounting / DoS

`configureRewardToken` allows de-whitelisting a token when `pendingRewards[token] <= 10`, but users may still hold nonzero `rewards[user][token]` for that token (earned but unclaimed). Once de-whitelisted, the token is removed from `rewardTokens`, so `_claimRewardsFor` no longer iterates it and the user's accrued rewards become permanently unclaimable. Conversely, if the token is re-whitelisted later, `pendingRewards[token]` may be less than the sum of outstanding `rewards[user][token]`, causing `pendingRewards[token] -= reward` to underflow and revert, bricking claims for all users of that token.

Attack path: 1) Attacker (any user) accrues rewards for token T. 2) Reward manager de-whitelists T (allowed because pendingRewards[T] <= 10 at that moment, even though user rewards exist). 3) User's rewards[T] is now orphaned. 4) If T is re-whitelisted, the first claimer triggers `pendingRewards[T] -= reward` underflow, reverting and blocking all claims for T.

Impact: Frozen/lost user rewards; permanent DoS on claimRewards for the affected token.

Recommendation: On de-whitelist, either require pendingRewards[token] == 0 and all user rewards to be zero, or keep the token in rewardTokens until all outstanding user rewards are claimed; also guard the subtraction.

Medium

SymmVesting getLiquidityQuote truncates usdcAmount and lpAmount

Model confidence: 60%

File: SymmVesting.sol

Function: getLiquidityQuote()

Category: Rounding direction

`usdcAmount = (symmAmount * usdcBalance) / symmBalance` truncates down, then `_mulDivUp(usdcAmount, 1e18, 1e30)` rounds up the decimal conversion. `lpAmount = (symmAmount * totalSupply) / symmBalance` truncates down. The `minLpAmountWithSlippage` default is `expectedLpAmount * 99 / 100`, so a 1% shortfall is tolerated. However, the actual `lpAmount` returned by the router is compared against `minLpAmountWithSlippage`, and if the router returns less than expected due to rounding, the user may receive fewer LP tokens than the SYMM they contributed — the difference is effectively donated to the pool. The truncation of `usdcAmount` also means the user may underpay USDC relative to the pool ratio, but the router's `addLiquidityProportional` will pull the correct amount, potentially reverting or taking more than quoted.

Attack path: 1) User calls `addLiquidity` with a `symmAmount` that produces a truncated `usdcAmount`. 2) Router pulls the actual proportional USDC (possibly more than quoted). 3) If `maxUsdcIn` is 0 (unlimited), the user pays more USDC than expected. 4) The `lpAmount` check uses the truncated `expectedLpAmount`, so slippage protection is weaker than intended.

Impact: Users can pay more USDC than quoted; LP token amounts can be lower than expected; slippage protection is weakened by truncation.

Recommendation: Round `usdcAmount` up and `lpAmount` down consistently, and use the router's returned `amountsIn` for the `maxUsdcIn` check.
