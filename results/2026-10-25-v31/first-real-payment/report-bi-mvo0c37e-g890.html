High

notifyRewardAmount lacks REWARD_MANAGER_ROLE check

Model confidence: 95%

File: SymmStaking.sol

Function: notifyRewardAmount()

Category: Missing Access Control

The `notifyRewardAmount` function is documented as a restricted function but has no access modifier. Any external caller can invoke it, transferring arbitrary whitelisted reward tokens from themselves into the contract and manipulating the reward rate/periodFinish for any whitelisted token. This lets an attacker grief existing stakers by extending the reward period with tiny amounts, diluting the rate, or resetting `lastUpdated`/`periodFinish` to disrupt accounting.

Attack path: 1) Attacker calls `notifyRewardAmount([whitelistedToken], [1])` repeatedly. 2) Each call transfers 1 wei of the reward token and calls `_addRewardsForToken`, which recomputes `state.rate = (amount + leftover) / state.duration` and resets `periodFinish = block.timestamp + duration`. 3) Existing stakers' effective reward rate is diluted and the period is perpetually extended, delaying full payout.

Impact: Reward accounting manipulation; stakers receive diluted rewards and the reward schedule can be indefinitely extended, effectively locking/diluting rewards.

Recommendation: Add `onlyRole(REWARD_MANAGER_ROLE)` to `notifyRewardAmount`.

High

Spot pool balances used for liquidity quote enable sandwich manipulation

Model confidence: 80%

File: SymmVesting.sol

Function: getLiquidityQuote()

Category: Spot-price manipulation

`getLiquidityQuote` derives `usdcAmount` and `expectedLpAmount` directly from `POOL.getCurrentLiveBalances()` and `POOL.totalSupply()`, which are instantaneous spot values. An attacker can skew the pool balances (e.g., via a large swap) right before a victim's `addLiquidity`/`addLiquidityByPercentage` call, causing the victim to pay more USDC and/or receive fewer LP tokens than fair. The `minLpAmount` default of 1% slippage is computed from the already-manipulated `expectedLpAmount`, so it does not protect against this.

Attack path: 1) Attacker flash-loans and swaps heavily into the SYMM/USDC pool to shift the ratio. 2) Victim calls `addLiquidity`; `getLiquidityQuote` returns inflated `usdcIn` and deflated `lpAmount`. 3) Victim's `maxUsdcIn` may be bypassed if 0, and `minLpAmountWithSlippage` is derived from the manipulated expected value. 4) Attacker reverses the swap and pockets the difference.

Impact: Victim loses USDC and receives fewer LP tokens; value extracted by attacker.

Recommendation: Use a TWAP or oracle-based quote, or require `minLpAmount`/`maxUsdcIn` to be user-supplied and non-zero, and compute slippage against a manipulation-resistant reference.

configureRewardToken can remove token with pending rewards <= 10

Model confidence: 75%

File: SymmStaking.sol

Function: configureRewardToken()

Category: Accounting / Access Control

When disabling a reward token, the code only reverts if `pendingRewards[token] > 10`. If pending rewards are between 1 and 10 (or exactly 10), the token is removed from `rewardTokens` while `pendingRewards[token]` remains nonzero. Since `_claimRewardsFor` iterates only over `rewardTokens`, users with small unclaimed rewards for that token can never claim them, and the residual balance is stranded.

Attack path: 1) A reward manager (or compromised role holder) disables a token while `pendingRewards[token]` is small (e.g., 5 wei). 2) The token is popped from `rewardTokens`. 3) Users with `rewards[user][token] > 0` call `claimRewards`, but the loop no longer includes the token, so their rewards are permanently unclaimable.

Impact: Users' earned rewards become permanently frozen in the contract; accounting mismatch between `pendingRewards` and claimable balances.

Recommendation: Require `pendingRewards[token] == 0` before removing a reward token, or allow claiming from a separate list of disabled tokens.

High

SymmStaking reward rate truncation causes stuck pendingRewards

Model confidence: 75%

File: SymmStaking.sol

Function: _addRewardsForToken

Category: Accounting/Rounding

When a new reward amount is added, `state.rate = amount / state.duration` truncates the division. The truncated remainder is never accounted for, so `pendingRewards[token]` (which is incremented by the full `amount`) will always exceed the sum of rewards actually distributable via `rate * duration`. Over time, `pendingRewards[token]` drifts above real claimable rewards, and `_claimRewardsFor` subtracts from `pendingRewards` based on user claims, eventually underflowing or leaving dust that blocks `configureRewardToken` (which reverts if `pendingRewards[token] > 10`).

Attack path: 1) Reward manager notifies a reward amount not divisible by `duration` (e.g., 1 week = 604800 seconds, amount = 604801). 2) `rate = 1`, distributable = 604800, but `pendingRewards += 604801`. 3) After all users claim, `pendingRewards[token]` still holds 1 wei. 4) Repeated notifications accumulate dust; once `pendingRewards[token] > 10`, `configureRewardToken(token, false)` reverts with `OngoingRewardPeriodForToken`, permanently preventing removal of the reward token.

Impact: Reward token cannot be delisted; accounting drift between `pendingRewards` and actual claimable rewards; potential underflow in `_claimRewardsFor` if `pendingRewards` is drained below actual claims.

Recommendation: Track distributable rewards separately from `pendingRewards`, or subtract the truncated remainder from `pendingRewards` when computing `rate`.

Medium

configureRewardToken bricks claims via unbounded rewardTokens array

Model confidence: 70%

File: SymmStaking.sol

Function: configureRewardToken()

Category: Denial of Service

`configureRewardToken` only allows removing a reward token when `pendingRewards[token] <= 10`, otherwise it reverts with `OngoingRewardPeriodForToken`. Combined with `rewardTokens.length` being used in every `_updateRewardsStates` and `_claimRewardsFor` loop over ALL reward tokens, an unbounded growing list (whitelisted via REWARD_MANAGER) makes every deposit/withdraw/claim gas-prohibitive. But since only the manager can whitelist, this alone is trusted. The untrusted angle: rewards are only fully drained when all stakers claim; pendingRewards is decremented only on claim, so a single dust-staker who never claims (or a griefer who deposits 1 wei and never claims their accruing reward) keeps `pendingRewards[token] > 10`, permanently preventing removal of that token — trapping the rewardTokens array size and any future removal.

Attack path: 1) Attacker deposits minimal stake (1 wei) before a reward token has periodFinish. 2) Attacker never calls claimRewards(). 3) Because rewards[attacker][token] stays > 0, pendingRewards[token] never drops to <=10. 4) Admin's configureRewardToken(token,false) reverts forever. 5) Reward list can never shrink, loops remain O(n) forever, all users pay growing gas.

Impact: Permanent inability to remove reward tokens; growing per-action gas for every user until deposits/withdrawals/claims become unaffordable and effectively freeze staking/claiming.

Recommendation: Allow removal regardless of pendingRewards and let users claim orphaned rewards via a per-token claim path, or use a global `rewardTokens` cap with explicit removal logic that doesn't depend on user cooperation.

File: Vesting.sol

Function: _claimUnlockedToken()

`_claimUnlockedToken` calls `IERC20(token).transfer(user, claimableAmount)` directly rather than using `SafeERC20.safeTransfer`. For tokens that do not return a boolean (e.g., USDT-like), this call reverts, permanently blocking claims for that token. Since the vesting contract supports arbitrary tokens (SYMM, SYMM_LP, and potentially others), this is a real compatibility issue.

Function: _addRewardsForToken()

`state.rate = amount / state.duration` (and the leftover branch) uses integer division. SymmAllocationClaimer claim() allows repeated claims via reentrancy-free but zero-allocation reset

Model confidence: 65%

File: SymmAllocationClaimer.sol

Function: claim()

Category: Accounting

`claim()` sets `userAllocations[msg.sender] = 0` after computing `amountToClaim`, but if `mintFactor < 1e18`, the difference `(userAllocations[msg.sender] - amountToClaim)` is added to `adminClaimableAmount`. If `mintFactor` is 0 (disallowed by constructor) this would be full allocation; with `mintFactor` small, `amountToClaim` can round to 0 for small allocations, and `userAllocations` is still zeroed. The user receives 0 tokens but loses their allocation, while `adminClaimableAmount` gains the full allocation. This is a rounding-direction issue that favors the admin over the user.

Attack path: 1) User has a small allocation such that `(allocation * mintFactor) / 1e18 == 0`. 2) User calls `claim()`. 3) `amountToClaim = 0`, `adminClaimableAmount += allocation`, `userAllocations[msg.sender] = 0`. 4) User receives 0 tokens and cannot claim again; admin can later mint the full allocation to the foundation.

Impact: User loses their entire allocation to the admin/foundation due to rounding; wrong accounting direction (favors protocol over user).

Recommendation: Revert if `amountToClaim == 0` in `claim()`, or round in favor of the user.

SymmVesting addLiquidityByPercentage rounds down, allowing dust griefing

Model confidence: 60%

File: SymmVesting.sol

Function: addLiquidityByPercentage

Category: Rounding

`amount = (getLockedAmountsForToken(msg.sender, SYMM) * percentage) / 1e18` truncates. If `percentage` is small or locked amount is small, `amount` can round to 0, then `_addLiquidityProcess` proceeds with `amount = 0`. `_addLiquidity` calls `getLiquidityQuote(0)` returning `usdcAmount = 0` and `lpAmount = 0`, then `ROUTER.addLiquidityProportional` is called with zero amounts. Depending on the router, this may revert or succeed with no effect, but `symmVestingPlan.resetAmount(symmLockedAmount - 0)` still runs, rebasing the vesting plan's start/end times without any actual liquidity added.

Attack path: 1) User calls `addLiquidityByPercentage` with a tiny `percentage` such that `amount` rounds to 0. 2) `_addLiquidityProcess` proceeds, calls `resetAmount` on the SYMM vesting plan, rebasing `startTime` to `block.timestamp` and `endTime` to `block.timestamp + remaining`. 3) User's vesting schedule is silently extended/reset without any liquidity added.

Impact: User's vesting schedule is unexpectedly rebased (extended) with no economic benefit; potential griefing of own or (via operator) others' plans.

Recommendation: Revert if `amount == 0` in `addLiquidityByPercentage` before calling `_addLiquidityProcess`.
