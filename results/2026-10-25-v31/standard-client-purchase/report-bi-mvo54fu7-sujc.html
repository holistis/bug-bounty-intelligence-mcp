Medium

SymmStaking reward rate truncation causes stuck pendingRewards

Model confidence: 70%

File: SymmStaking.sol

Function: _addRewardsForToken()

Category: Rounding / Accounting drift

When a new reward amount is added, `state.rate = amount / state.duration` (or `(amount + leftover) / state.duration`) truncates the remainder. The full `amount` is added to `pendingRewards[token]`, but the sum of `rate * duration` distributed over time is less than `amount`. The truncated dust is never claimable, so `pendingRewards[token]` permanently exceeds the sum of all users' claimable rewards, and `_claimRewardsFor` will eventually underflow when the last claimer tries to subtract their reward from a `pendingRewards` that is smaller than the sum of individual rewards.

Attack path: 1) Reward manager notifies a reward amount not divisible by `duration` (e.g. 1 wei over a week). 2) `rate` truncates, dust remains in `pendingRewards`. 3) Over many notifications the drift accumulates. 4) When users claim, `pendingRewards[token] -= reward` can underflow (revert) once the accumulated truncation exceeds the remaining balance, freezing claims for that token.

Impact: Users cannot claim rewards (DoS on `claimRewards`/`claimFor`), and `pendingRewards` accounting permanently diverges from real distributable rewards.

Recommendation: Track the undistributed remainder and roll it into the next notification, or compute `rate` from the actual distributable amount and reduce `pendingRewards` accordingly.

High

claimRewards reverts on zero-amount reward transfer, blocking all rewards

Model confidence: 70%

File: SymmStaking.sol

Function: _claimRewardsFor()

Category: Denial of Service / Revert on zero transfer

`_claimRewardsFor` iterates over ALL reward tokens and calls `IERC20(token).safeTransfer(user, reward)` whenever `reward > 0`. Many ERC20 tokens (e.g. those using OpenZeppelin's `_transfer` with a zero-value revert, or tokens that revert on zero transfers like some ERC20 implementations) will revert. More critically, if a whitelisted reward token is later deprecated or its transfer is blocked (blacklist, paused token), the loop cannot complete; the entire `claimRewards()` call reverts, preventing the user from claiming ANY reward token, and `pendingRewards[token]` stays recorded forever.

Attack path: (1) An attacker (or any user) is unable to claim rewards for a token whose transfer logic reverts (e.g., token that reverts on zero transfer to the user, or a blacklisted/pausable reward token). (2) `_claimRewardsFor` reverts mid-loop, reverting the entire `claimRewards()` transaction. (3) Even for whitelisted tokens later blocked, no mechanism exists to skip or quarantine the offending token, so users cannot claim any rewards.

Impact: Users permanently unable to claim any staking rewards from any reward token; funds effectively frozen in the contract. The reward token list is also not removable because `configureRewardToken` reverts when `pendingRewards[token] > 10`.

Recommendation: Wrap each transfer in a try/catch or check `token` balance/eligibility before transfer; alternatively allow removing a reward token from the iteration (or skipping failing tokens) so a single bad token can't block claims.

High

Reward rate dilution via notifyRewardAmount during active period

Model confidence: 70%

File: SymmStaking.sol

Function: notifyRewardAmount()

Category: Reward accounting / incentive gaming

When a new reward notification arrives while a period is still active, `_addRewardsForToken` computes `state.rate = (amount + leftover) / state.duration` and then extends `periodFinish = block.timestamp + state.duration`. The `leftover` is computed as `remaining * state.rate` using the OLD rate, but the new rate is then applied over a full fresh `duration` window, so the total emitted rewards over the new window can exceed `amount + leftover` (or under-emit), and the per-second rate is reset to a value that does not preserve the previously accrued entitlement. Because `_updateRewardsStates(address(0))` is called before the loop, existing stakers' `perTokenStored` is snapshotted, but the new rate is applied to the entire new duration including time that was already accounted for at the old rate, causing double-counting or under-counting of rewards relative to the tokens actually deposited.

Attack path: 1) Attacker (a staker) waits until a reward period is near its end with a large `leftover`. 2) Attacker (or any reward manager, but the flaw is exploitable by timing) triggers `notifyRewardAmount` with a tiny amount, which resets `periodFinish` to `block.timestamp + duration` and recomputes `rate` using the leftover. 3) The new rate is applied over the full new duration, so the attacker's share of rewards is computed against a rate that does not correspond to the actual tokens funded for that window. 4) Attacker claims at the optimal moment to capture more than their pro-rata share, leaving the contract short for other stakers.

Impact: Reward token insolvency — the contract can owe more rewards than it holds, causing later claimants' `safeTransfer` to revert and freezing rewards for honest stakers.

Recommendation: Compute the new rate as `(amount + leftover) / duration` only when `block.timestamp >= periodFinish`; otherwise extend `periodFinish` by `amount / state.rate` (or use a proper accumulator) so the leftover is consumed at the old rate before the new rate applies.

Model confidence: 60%

File: SymmVesting.sol

Function: _addLiquidity()

Category: Slippage / accounting

`expectedLpAmount` is computed from `getLiquidityQuote` using current pool balances, then passed directly to `ROUTER.addLiquidityProportional` as the minimum LP amount. SymmAllocationClaimer adminClaimableAmount can be gamed by claim timing

Model confidence: 60%

File: SymmAllocationClaimer.sol

Function: claim()

Category: Reward epoch / incentive gaming

In `claim()`, `amountToClaim = (userAllocations[msg.sender] * mintFactor) / 1e18` and `adminClaimableAmount += (userAllocations[msg.sender] - amountToClaim)`. Medium

claimLockedToken penalty is transferred from contract balance, not from user's claim

Model confidence: 55%

File: Vesting.sol

Function: _claimLockedToken()

Category: Accounting / fee handling

`_claimLockedToken` computes `penalty = (amount * lockedClaimPenalty) / 1e18`, then transfers `amount - penalty` to the user and `penalty` to `lockedClaimPenaltyReceiver`. Both transfers come from the contract's balance, and `totalVested[token] -= amount` only accounts for the gross amount. If the contract's balance is insufficient (e.g., because `_ensureSufficientBalance` only mints the deficit for `amount`, not for the penalty separately), the penalty transfer can fail or drain funds earmarked for other users' vesting. More importantly, the penalty is taken from the contract's pooled balance rather than being deducted from the user's own vested entitlement, so other users effectively subsidize the penalty.

Attack path: 1) Attacker sets up a vesting plan with a small amount. 2) Attacker calls `claimLockedToken` for the full locked amount. 3) The penalty is paid out of the contract's pooled balance, which includes other users' vested tokens. 4) If the contract is underfunded, the transfer reverts, but if overfunded, the attacker's penalty is effectively paid by others. 5) Repeated claims by many users can drain the pool.

Impact: Cross-user subsidy of penalties; potential insolvency if penalties exceed the contract's free balance; `totalVested` accounting does not reflect the penalty outflow.

Recommendation: Deduct the penalty from the user's vested amount before transferring, i.e., reduce `totalVested[token]` by `amount` and transfer `amount - penalty` to the user and `penalty` to the receiver, ensuring the contract's balance is sufficient for both.
