SymmStaking.rescueTokens allows admin to drain staking and reward tokens

Model confidence: 90%

File: SymmStaking.sol

Function: rescueTokens()

Category: Privileged Setter / Trust

`rescueTokens` is guarded only by `DEFAULT_ADMIN_ROLE` and transfers any `token` to any `receiver` without excluding `stakingToken` or whitelisted reward tokens. The admin (or anyone who obtains the role, e.g., via the initializer front-run above) can drain the entire staked SYMM balance and all pending reward tokens, leaving users unable to withdraw or claim. Attack path: 1) Attacker obtains `DEFAULT_ADMIN_ROLE` (via initializer front-run or compromised admin). 2) Calls `rescueTokens(stakingToken, balanceOf(contract), attacker)`. 3) All staked SYMM is transferred out; users' `withdraw` calls revert due to insufficient balance.

Impact: Complete loss of all staked user funds and pending rewards. Contract becomes insolvent.

Recommendation: Disallow rescuing `stakingToken` and whitelisted reward tokens, or route rescue through a timelock with a delay.

High

SymmVesting.initialize is public and can be re-initialized via front-run

Model confidence: 85%

File: SymmVesting.sol

Function: initialize()

Category: Initializer / Access Control

`SymmVesting.initialize` is declared `public initializer` (not `external`), and the contract inherits `Vesting` which also exposes `__vesting_init` as `public initializer`. If the proxy is deployed and `initialize` is not called atomically in the same transaction, any untrusted actor can call `initialize` first and become `DEFAULT_ADMIN_ROLE`, `SETTER_ROLE`, `OPERATOR_ROLE`, `PAUSER_ROLE`, `UNPAUSER_ROLE`, and set `lockedClaimPenaltyReceiver` to themselves. The `initializer` modifier only prevents re-entry after the first successful call, so the first caller wins.

Attack path: 1) Deployer deploys proxy + implementation but does not call `initialize` in the same tx (common with multisig/timelock setups). 2) Attacker front-runs by calling `SymmVesting.initialize(attacker, attacker, ...)` with valid non-zero addresses. 3) Attacker now holds all roles, can pause, set penalty receiver, and call `setupVestingPlans`/`resetVestingPlans` to mint/allocate tokens to themselves.

Impact: Full takeover of the vesting contract: attacker can grant themselves vesting plans, drain via `_ensureSufficientBalance` minting path (SYMM mint), and redirect penalties. Complete loss of funds and control.

Recommendation: Make `initialize` `external` and ensure deployment scripts call it atomically; consider using `_disableInitializers()` in the implementation constructor.

Medium

SymmStaking reward rate truncation causes stuck pendingRewards

Model confidence: 85%

File: SymmStaking.sol

Function: _addRewardsForToken()

Category: Rounding / Accounting drift

`state.rate = amount / state.duration` truncates the per-second rate, so `rate * duration < amount`. The difference between the notified `amount` (added to `pendingRewards[token]`) and the total rewards actually distributed (`rate * duration`) is never claimable, leaving `pendingRewards[token]` permanently larger than the sum of user rewards. This also blocks `configureRewardToken(token, false)` because the check `pendingRewards[token] > 10` will keep reverting.

Attack path: 1) Reward manager notifies a small amount (e.g. 604799 wei over 1 week) — rate becomes 0, entire amount stuck. 2) Even for normal amounts, the truncated remainder accumulates in `pendingRewards` forever. 3) Any attempt to delist the token reverts with `OngoingRewardPeriodForToken` because `pendingRewards[token]` never reaches ≤10.

Impact: Reward tokens permanently locked in the contract; reward token cannot be removed from the whitelist; accounting drift between `pendingRewards` and actual claimable rewards.

Recommendation: Track the undistributed remainder and roll it into the next notification, or compute `rate` such that `rate * duration == amount` (e.g. store `amount` and distribute proportionally), and reconcile `pendingRewards` against actual claims.

High

Reverting reward token blocks all deposits/withdrawals/claims

Model confidence: 85%

File: SymmStaking.sol

Function: _claimRewardsFor()

Category: Denial of Service

`_claimRewardsFor` iterates over `rewardTokens` and calls `IERC20(token).safeTransfer(user, reward)` for each token with a positive reward. Because every user-triggerable state function (`deposit`, `withdraw`, `claimRewards`) calls `_updateRewardsStates` and (for claims) `_claimRewardsFor`, if any single whitelisted reward token starts reverting on transfer (e.g., a blacklistable/pausable token like USDC/USDT with the user blacklisted, or a token that simply reverts), every staker becomes permanently unable to deposit, withdraw, or claim. There is no per-token try/catch or skip logic.

Attack path: 1) A reward token with blacklist functionality (e.g., USDC) is whitelisted by the manager. 2) Attacker contracts/stakes a small amount, accrues reward, then arranges (via external token admin action or self-blacklisting path where available) to have the reward transfer revert for themselves — or more generally relies on a token whose transfer path can revert. 3) Any subsequent call to `withdraw`, `deposit`, or `claimRewards` by that user reverts in `_claimRewardsFor`, trapping their staked principal and blocking further interactions. Because `_updateRewardsStates` also processes all reward tokens in the loop, a single problematic token also inflates gas and can revert entire multi-token operations.

Impact: Staked principal becomes stuck; users cannot withdraw staking tokens or claim remaining rewards; the entire staking contract's core flows become unusable for affected users and potentially globally if the reverting token is processed in `_updateRewardsStates`.

Recommendation: Handle reward transfers per-token with a try/catch or allow claiming individual reward tokens, and never let a single reward token's transfer failure revert `deposit`/`withdraw`.

Medium

SymmStaking notifyRewardAmount extends period without accounting for leftover

Model confidence: 70%

File: SymmStaking.sol

Function: _addRewardsForToken()

Category: Reward accounting / double counting

When a new notification arrives mid-period, `leftover = remaining * state.rate` is added to `amount` and divided by the full `duration`, but `pendingRewards[token]` is incremented by the full new `amount` only. The leftover portion was already counted in `pendingRewards` from the previous notification, so the new `rate` distributes `(amount + leftover)` over `duration` seconds while `pendingRewards` only reflects `amount` — the extra `leftover` is distributed to users but never decremented from `pendingRewards` on claim, causing `pendingRewards[token]` to underflow on the final claim.

Attack path: 1) Notify 100 tokens for 1 week. 2) After 3 days, notify another 100 tokens. 3) `leftover ≈ 57` is added to `amount`, so `rate = 157/1week`. 4) Users claim rewards totaling ~157, but `pendingRewards` was only incremented by 100+100=200 minus claims... actually the leftover is double-counted in the rate but not in pendingRewards, so the last claimer's `pendingRewards[token] -= reward` underflows and reverts, freezing their rewards.

Impact: Last claimer cannot claim (revert on underflow), rewards frozen; `pendingRewards` accounting diverges from real token balance.

Recommendation: When extending, subtract the already-accounted leftover from `pendingRewards` before adding the new amount, or recompute `pendingRewards` consistently with the new rate and remaining duration.

unbounded rewardTokens array DoS on every user action

Model confidence: 70%

File: SymmStaking.sol

Function: _updateRewardsStates()

Category: Gas Limit / DoS

Every state-changing user path (`deposit`, `withdraw`, `claimRewards`) calls `_updateRewardsStates`, which loops over the full `rewardTokens` array and calls `rewardPerToken` (which itself reads storage for each token). `rewardTokens` is growable via `configureRewardToken` (bounded only by manager's willingness). Impact: Staked principal and pending rewards become unrecoverable because `withdraw` cannot complete within block gas limits. Permanent liveness failure of the core contract.

Recommendation: Cap the number of reward tokens, or refactor to per-user reward token tracking so each user only iterates over tokens they actually accrue.

High

Reward rate dilution via notifyRewardAmount during active period

Model confidence: 70%

File: SymmStaking.sol

Function: notifyRewardAmount()

Category: Reward epoch manipulation

When a reward period is still active, `_addRewardsForToken` computes `state.rate = (amount + leftover) / state.duration` and then resets `periodFinish = block.timestamp + state.duration`. This extends the period by a full `duration` while spreading the leftover over the new full duration, effectively diluting the rate for existing stakers and stretching the tail. A reward manager (or anyone with the role) can repeatedly top-up small amounts to keep extending the period and reduce per-second emissions, but more importantly the leftover accounting is wrong: `leftover = remaining * state.rate` uses the OLD rate, but the new rate is applied over the FULL new duration, so the total emitted over the new window is `rate * duration` which can exceed `amount + leftover` when `remaining < duration`. This causes the contract to promise more rewards than it holds.

Attack path: 1) Attacker (with REWARD_MANAGER_ROLE, or via a compromised/legit manager) calls `notifyRewardAmount` with a tiny amount while a period is active. 2) `leftover = remaining * oldRate` is computed, then `newRate = (tiny + leftover) / duration`. 3) Because `remaining < duration`, the new rate applied over the full `duration` emits `newRate * duration = tiny + leftover` — but the actual tokens held are only `tiny + leftover` and the previous period already emitted up to `block.timestamp`. The math over-emits relative to the remaining schedule, and repeated calls compound the discrepancy. 4) Stakers claim more than was deposited, draining other reward tokens or reverting claims.

Impact: Reward token insolvency — `pendingRewards[token]` underflows on claim, or claims revert, or the contract pays out more than deposited, draining other reward token balances.

Recommendation: Compute the new rate as `(amount + leftover) / duration` only when starting fresh; when extending, use `(amount + leftover) / (remaining + duration)` or keep `periodFinish` unchanged and add `amount / remaining`.
