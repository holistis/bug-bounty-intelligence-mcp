# Audit report

## [High] sqrt() uses assembly stop() for zero input and halts the whole calling transaction

File: Float128.sol
Function: sqrt()

`sqrt` is an internal library function inlined into the caller. For a == 0 it runs `if iszero(a) { stop() }` inside the assembly block. `stop()` terminates the entire EVM execution context successfully; it does not return zero from the function. Any code in the caller after `Float128.sqrt(0)` is skipped, including later state updates and checks. The external call returns success with empty return data. A caller that expects a decoded return value will either revert or behave unpredictably, depending on how it handles the empty data.

Attack path: 1. A contract function computes `Float128.sqrt(x)` on a value that can be zero, for example a variance, a reserve product or a zero-balance input.
2. A user supplies or arranges x = 0.
3. Execution stops with success at the sqrt call, skipping the remaining logic. Intended invariant checks, state writes or transfers after it never run.

Impact: Remaining logic can be bypassed, for example checks placed after the sqrt call. The call also returns success with empty data instead of 0, which can leave state inconsistent or break integrations.

## [High] add/sub subtraction path returns a 72-digit mantissa without the L flag for large operands

File: Float128.sol
Function: add() / sub()

In the subtraction branch (`isSubtraction`), the unnormalized `addition` is already a valid 72-digit L mantissa when it lies in [MIN_L_DIGIT_NUMBER, MAX_L_DIGIT_NUMBER]. The `else if` then only handles the case `rExp < 8140`, where it divides by 10^34 to produce an M result. When `rExp >= 8140` (L operands with exponent >= -52) nothing sets MANTISSA_L_FLAG_MASK. `r` was built only from the exponent bits and the sign bit, so it never carries the flag from the inputs. The final `r := or(r, addition)` therefore encodes a 72-digit mantissa as an M-size float. Every later decode reads the value 10^34 times too large. The condition is hit whenever two large L numbers (value >= ~1e24) cancel by about 4 to 5 leading digits, for example 1.0005e30 - 1.0e30. `sub()` has an identical copy of the code.

Attack path: 1. A protocol using Float128 stores or computes two large L-size floats (value above ~1e24) that agree in their first ~4 digits.
2. Anyone who can influence those inputs calls a function that does `a.sub(b)`, or `a.add(b)` with opposite signs.
3. The result is a float with a 72-digit mantissa and no L flag.
4. Subsequent mul, div, comparisons and decode treat it as ~1e34 times larger, corrupting any accounting built on it.

Impact: Silent mis-scaling by 10^34 of subtraction results for large values. This can inflate or deflate balances, prices or other quantities and corrupt every dependent computation.

## [Medium] ln(0) does not revert and returns a large finite negative number (~ -18,797)

File: Ln.sol
Function: ln()

ln() only special-cases the exact value 1 and never checks for zero. A packedFloat of 0 decodes as mantissa 0 and exponent -8192. ln_helper sends it to the 'x<1' branch, where m10 = 38 + (-8192) = -8154. The mantissa then stays 0 after `mantissa *= 1e38`, so k=3 and calculateQ1/Q2/Q3 return q1=q2=q3=7 with updated mantissa 0. In intermediateTermAddition, z_int = 10**76 - 0 gives z = 1 exactly, so the series is the harmonic sum 1+1/2+...+1/15. finalTermAddition then adds 3*ln2 + 7*ln1.1 + 7*lnB + 7*lnC + 8154*ln10 and negates. The function returns about -18.8e3 instead of reverting or signalling -infinity.

Attack path: 1. A downstream contract (pricing, interest, bonding curve) calls Ln.ln(packedFloat 0), either because a user-controlled amount or ratio is zero or because an intermediate result underflows to 0. 2. ln returns a finite, very negative number with no revert. 3. The caller continues with it, for example as an exponent or a fee/price term, and uses a bogus value.

Impact: Silent wrong results for a mathematically undefined input. Any consumer that relies on a revert for ln(0) can be fed a finite value that is wrong by thousands, which can distort pricing or accounting.

## [Medium] ln() ignores the sign bit, so ln(-x) silently returns ln(x)

File: Ln.sol
Function: ln()

ln() extracts the L flag, the mantissa (`and(input, MANTISSA_MASK)`) and the exponent, but never reads MANTISSA_SIGN_MASK (bit 240), which is the sign bit in the packed format. A negative packedFloat therefore takes exactly the same path as its absolute value. The early return for 1 also fires for -1, so ln(-1) returns 0 instead of reverting. The logarithm of a negative number is undefined, and Float128.sqrt, for comparison, does revert on negative inputs.

Attack path: 1. A caller passes a negative packedFloat to ln(), for example the result of a subtraction that went negative, or a user-supplied negative value. 2. ln() returns ln(|x|) with no error. 3. The caller treats it as valid.

Impact: Wrong results instead of failure for out-of-domain inputs. This can enable manipulation of any formula that takes ln of a value that can become negative.

## [Medium] sqrt() high-exponent path halves an odd pre-exponent after incrementing it, giving a result off by 10x

File: Float128.sol
Function: sqrt()

In the large-exponent branch the code makes `aExp` even and sets `rExp = aExp - 72`. If `rMan > MAX_L_DIGIT_NUMBER` it does `rMan /= BASE; ++rExp` and only afterwards does `rExp = rExp / 2`. The correct exponent is (aExp-72)/2 + 1, which means adding 2 before halving. Adding 1 gives an odd value, and Solidity signed division truncates toward zero. For negative values this happens to be right. For non-negative `rExp`, when original aExp >= 73, the result is one lower than correct. The extra digit occurs for every odd original exponent, since those get `aMan *= BASE`.

Attack path: 1. A caller takes sqrt of an L float with odd exponent >= ~73, i.e. a value of roughly 1e144 or more (for example 1.5e145).
2. The result comes back with exponent one too low, so it is 10 times too small.

Impact: The square root of very large numbers with odd exponents is wrong by a factor of 10. The exact threshold needs checking, and the range may be unusual in practice.

## [Medium] Non-canonical float encodings: L/M boundary off-by-one and inconsistent normalization break raw eq()

File: Float128.sol
Function: eq() / add() / sub() / toPackedFloat()

`eq` compares raw words, so it relies on a unique encoding for each value. The encoding is not unique. First, the subtraction normalization converts an L-range result to M only when `rExp < 8140`, i.e. exponent < -52. An L number with exponent exactly -52 should become M with exponent -18, which toPackedFloat accepts, and it stays L instead. Second, the subtraction branch leaves a 38-digit mantissa that is already in M range as M even when its exponent is greater than -18 (reachable for L operands with heavy cancellation), whereas toPackedFloat would flag it L. Third, `toPackedFloat` leaves any mantissa already in [10^71, 10^72) as L even when exponent <= -52, while the arithmetic ops would turn the same value into M. The same numeric value therefore has several different words.

Attack path: 1. A contract compares a computed result against a constant built with toPackedFloat (or against another computed value) using `Float128.eq` or a raw word comparison.
2. Equal values encoded differently compare unequal, so equality-based checks fail or can be dodged.

Impact: Equality checks, mapping keys and other raw-word comparisons give wrong results for equal values. Zero-balance or threshold checks built on eq can misbehave.

## [Medium] ln() truncates large-mantissa (L) inputs ≥1 to 38 digits, losing the precision the docs promise

File: Ln.sol
Function: ln_helper()

The NatSpec says a large-mantissa input gives better precision. In the branch for x≥1 (`MAX_DIGITS_L > positiveExp`), an L input is first cut with `mantissa /= BASE_TO_THE_DIGIT_DIFF` and `exp += 34`, which drops 34 digits before the reciprocal is computed. Only inputs below 1 keep the full 72 digits, via `mantissa *= BASE_TO_THE_DIFF_76_L`. For an L input slightly above 1, such as 1+1e-40, the truncated mantissa equals exactly 1e37 and the result is 0 instead of about 1e-40. Even outside that case, results for x>1 carry only about 38 digits of the input. The precision is also asymmetric: ln(x) and -ln(1/x) differ greatly in accuracy for L values near 1.

Attack path: 1. A caller passes an L-size value just above 1, for example a compounding or growth factor with 70 decimals. 2. ln_helper cuts it to a 38-digit mantissa. 3. The result is 0 or badly rounded, so the caller's log-based computation loses the small increment entirely.

Impact: Incorrect logarithms (up to total loss of the signal near 1) for high-precision inputs above 1. This breaks any use that depends on the L precision, such as interest accrual.

## [Medium] le()/ge() return false for equal values when mantissa/flag encodings differ (lt/gt reused on tie)

File: Float128.sol
Function: le() / ge()

le() and ge() return true only if the raw words are identical. Otherwise, when signs match and exponents match after M-to-L scaling, they set retVal := lt(aMan,bMan) (le) or lt(bMan,aMan) (ge). Those are strict comparisons, so two equal values with different raw encodings come out false. toPackedFloat keeps any 72-digit mantissa as an L float even when an M encoding is canonical, so toPackedFloat(10**71,-71) is not the raw word of toPackedFloat(1,0). The same happens with the unflagged 72-digit results of add/sub. For such a pair, lt, gt, le, ge and eq are all false, so the comparison functions no longer give a total order. The non-strict tie case in le/ge was never written.

Attack path: 1) A caller builds the same value in two ways, for example toPackedFloat(10**71,-71) as an L float and toPackedFloat(1,0) as an M float. A value computed by mul, div or add can produce the same effect. 2) A consumer guard such as require(a.le(limit)) or require(a.ge(min)) is run on them. 3) The guard fails on the exact boundary, or a boundary branch is skipped.

Impact: Threshold and limit checks that depend on <= or >= misbehave at the boundary for equal numbers in different encodings. Callers can be denied service or can bypass a branch, depending on how the caller uses the result.

## [Medium] No exponent range checks: overflow or underflow of the 14-bit exponent wraps silently and corrupts encoding

File: Float128.sol
Function: mul() / div() / toPackedFloat() / add()

The exponent is stored in the top 14 bits (offset 8192). `mul` computes `rExp = aField + bField - ZERO_OFFSET` and `div` computes `rExp = (aExp + ZERO_OFFSET) - bExp`, the latter in an `unchecked` block. `toPackedFloat` adds ZERO_OFFSET to a caller-supplied exponent. All of them then do `shl(EXPONENT_BIT, rExp)` and OR the result in with no bounds check. A result exponent outside [-8192, 8191] wraps silently modulo 2^14 (excess bits are shifted out). An underflowing value, for example a tiny number, turns into a huge one, and the reverse. No revert occurs.

Attack path: 1. An attacker supplies very large or very small floats, or a user-controlled exponent to toPackedFloat.
2. Chained mul/div pushes the exponent past the range.
3. The wrapped result is a value of completely different magnitude.

Impact: Silent wrong magnitudes, for example tiny values becoming huge, whenever extreme values can be reached.
