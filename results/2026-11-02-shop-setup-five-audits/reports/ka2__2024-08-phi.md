# Audit report

## [High] Public _addCredIdPerAddress/_removeCredIdPerAddress let anyone corrupt a holder's index and block full sells

File: Cred.sol
Function: _removeCredIdPerAddress()

`_addCredIdPerAddress` and `_removeCredIdPerAddress` are declared `public` with no access control, even though they are internal bookkeeping helpers. Anyone can call them for any `sender_`. A call to `_removeCredIdPerAddress(credId, victim)` removes the entry from the victim's `_credIdsPerAddress` array and deletes `_credIdsPerAddressCredIdIndex`, while the victim's `shareBalance` and `_credIdExistsPerAddress` stay true. When the victim later sells their whole position, `_updateCuratorShareBalance` calls `_removeCredIdPerAddress` again. It reads index 0 from the deleted mapping and reverts with `EmptyArray` if the array is empty, or with `WrongCredId` if slot 0 holds another cred. `_addCredIdPerAddress` can also push junk or duplicate entries and overwrite the index mapping, and it uses `_credIdsPerAddressArrLength`, which is also manipulable.

Attack path: 1. Victim buys shares of cred X. 2. Attacker calls `_removeCredIdPerAddress(X, victim)` directly. 3. Victim calls `sellShareCred` or `batchSellShareCred` for their full balance. 4. `_updateCuratorShareBalance` reverts on the removal helper, so the full position can never be sold. Only a partial sell that leaves at least one share works. Any batch sell containing that cred also reverts.

Impact: An attacker can cheaply lock any holder out of fully exiting a position, or make a batch sell revert. This also corrupts the position index used by `getPositionsForCurator`.

## [High] Claims never check prior minting, so signatures/Merkle proofs can be replayed and quantity is unsigned

File: PhiFactory.sol
Function: signatureClaim() / merkleClaim() / _validateAndUpdateClaimState()

`_validateAndUpdateClaimState` writes `artMinted[artId_][minter_] = true` and `credMinted` but never reads them. The `AddressAlreadyMinted` error is never used. The signature payload is `(expiresIn, minter, ref, verifier, artId, chainid, data)` and has no nonce, and nothing marks it as used. The Merkle leaf is just `(minter, leafPart)`. `quantity` and `imageURI` come from the unsigned `MintArgs` and are not covered by the signature or the leaf. The same valid signature or proof can be submitted repeatedly until the signature expires. For Merkle claims the proof never expires, so it can be reused indefinitely. The caller can also pick any `quantity`, up to `maxSupply`.

Attack path: 1. A minter obtains one valid signature or Merkle proof for a cred. 2. They call signatureClaim/merkleClaim again and again, or with quantity set to the whole remaining supply. 3. They pay only the per-unit mint fee and need no further eligibility. 4. Anyone who sees a signature or proof in the mempool or API can also reuse it for that minter.

Impact: Each cred is meant to be proven once per minter, but eligibility becomes unlimited. Supply can be drained by a single eligible address, and the one-per-cred intent is broken.

## [Medium] buyShareCredFor / batchBuyShareCred reset victim's share lock, letting anyone block selling indefinitely

File: Cred.sol
Function: _handleTrade()

`buyShareCredFor` and `batchBuyShareCred` let any caller buy shares for an arbitrary `curator_`. Both set `lastTradeTimestamp[credId][curator_] = block.timestamp`. The sell path requires `block.timestamp > lastTradeTimestamp[credId][curator_] + SHARE_LOCK_PERIOD` (10 minutes). The lock timer of the recipient is therefore controlled by third parties, with no consent from the recipient.

Attack path: Attacker calls `buyShareCredFor(credId, 1, victim, 0)` at least every 10 minutes. Each call restarts the victim's lock, so the victim's `sellShareCred` and `batchSellShareCred` revert with `ShareLockPeriodNotPassed`. The attacker only pays the price of one share, and the shares they gift are worth the same on the curve.

Impact: A victim can be prevented from selling for as long as the attacker keeps this up. The attacker can do this during a price drop or around a rug.

## [Medium] getPositionsForCurator writes results at index i instead of the running index

File: Cred.sol
Function: getPositionsForCurator()

The result arrays are allocated with length `stopIndex - start_`, but the loop writes `credIds[i]` and `amounts[i]` with `i` running from `start_` to `stopIndex`, not the running `index`. Any call with `start_ > 0` indexes past the array and panics. If an entry is skipped, the data is left misaligned, because `mstore` then truncates the arrays to `index` while the entries sit at other positions. The paginated view is therefore broken for every page except the first.

Attack path: A frontend or contract calls `getPositionsForCurator(user, 1, 0)` for a user with at least 2 positions. The call reverts with an out-of-bounds panic.

Impact: A user's positions cannot be paginated. Integrations that depend on this view get reverts or wrong data.

## [High] claim()/batchClaim() ignore msg.value and pay mint fees from the factory's own ETH balance

File: PhiFactory.sol
Function: claim() / batchClaim()

`claim` computes `mintFee = getArtMintFee(...)` and calls `this.merkleClaim{value: mintFee}` or `this.signatureClaim{value: mintFee}`. It never checks `msg.value >= mintFee`, and the forwarded value does not come from the caller's msg.value. The inner `msg.value < getArtMintFee` check in `_validateAndUpdateClaimState` therefore always passes, because the factory sends exactly `mintFee` of its own balance. `batchClaim` only checks `sum(ethValue_) == msg.value` and forwards `ethValue_[i]` to `claim`, which ignores it. Any ETH held by the factory pays for these claims. The factory can build up a balance because `claim` and `batchClaim` keep any overpayment, the factory has no refund path for them, and the balance can also be forced in by selfdestruct. The owner's `withdraw()` is what normally empties it.

Attack path: 1. Overpaid ETH accumulates in the factory from earlier `claim`/`batchClaim` calls. 2. An attacker calls `claim` or `batchClaim` with msg.value = 0 and ethValue_ = 0 for valid claim data. 3. The factory sends its own ETH as the mint fee and the attacker mints without paying.

Impact: Other users' overpayments are drained, and mints become free while the factory holds ETH. Users who overpay in `claim`/`batchClaim` also lose the excess, with no refund.

## [Medium] createArt signature does not cover CreateConfig and is replayable, so anyone can create arts and reset Merkle roots

File: PhiFactory.sol
Function: createArt() / _validateArtCreationSignature() / _initializePhiArt()

The signed data is `(expiresIn, uri, credData)` and does not include `createConfig_`. It has no chainId, no nonce, and no binding to msg.sender. `createConfig_` holds `artist`, `receiver`, `maxSupply`, `mintFee`, the times and `soulBounded`, and the caller supplies all of these freely. `_initializePhiArt` also overwrites `credMerkleRoot[credChainId][credId]` with the root from the signed data on every call.

Attack path: 1. A cred creator's signed data becomes visible, for example in a mempool or API response. 2. An attacker front-runs or replays it with their own artist/receiver/mintFee/maxSupply. 3. Each replay creates another art entry for the cred before the signature expires. 4. Replaying older signed data for the same cred resets `credMerkleRoot` to a stale root, breaking or changing which Merkle claims are valid.

Impact: Unauthorized arts are created with attacker-chosen parameters and art IDs are consumed. The attacker becomes `artist` and can call `updateArtSettings`. Merkle verification for a cred's other arts can be corrupted. Signed data can also be replayed across chains.

## [Medium] Refund goes to the NFT contract when claims use Claimable on PhiNFT1155, so excess ETH is stuck

File: Claimable.sol
Function: signatureClaim() / merkleClaim()

In `Claimable`, the NFT contract forwards `msg.value` to the factory's `signatureClaim`/`merkleClaim`. `_processClaim` refunds `etherValue_ - mintFee` to `_msgSender()`, which is the NFT contract. PhiNFT1155 has a `receive()` but no function to withdraw or forward ETH. The `msg.sender == art.artAddress` exemption in the tx.origin check also lets any contract caller bypass the EOA-only restriction through this path.

Attack path: 1. A user calls `PhiNFT1155.signatureClaim` or `PhiNFT1155.merkleClaim` with msg.value above the fee. 2. The factory refunds the excess to the NFT contract. 3. The ETH stays in the NFT contract permanently.

Impact: Users lose any overpayment. The tx.origin check is bypassable by contracts through this path.

## [Medium] Curator rewards can be captured by just-in-time share purchase, atomically via buy-refund reentrancy

File: CuratorRewardsDistributor.sol
Function: distribute()

distribute() pays out the whole accumulated balanceOf[credId] pro rata to getShareNumber() at the moment of the call. There is no time weighting, and the only defence is Cred's 10-minute SHARE_LOCK_PERIOD. In Cred._handleTrade (buy path), the excess-payment refund `_msgSender().safeTransferETH(excessPayment)` runs before `lastTradeTimestamp[credId_][curator_] = block.timestamp` is written, and the single-buy path has no nonReentrant. In the refund callback the buyer sees new shares already counted but the old lock timestamp still in place, so the sell lock check passes. The buyer can call distribute() and then sellShareCred() inside the same transaction.

Attack path: 1) Wait until the distributor balanceOf[credId] has accumulated mint rewards. 2) From a contract, call Cred.buyShareCred for many shares with excess ETH. 3) In receive(), call distribute(credId), which credits most of the pot to the attacker's contract. 4) Still in receive(), call sellShareCred for all shares; the lock check uses the stale timestamp. 5) Withdraw the credited amount from PhiRewards. The attacker pays only the round-trip protocol and creator fees. Even without reentrancy, buying, calling distribute() and selling after 10 minutes works.

Impact: Long-term curators lose most of the accumulated curator rewards to a flash participant. The 10-minute lock does not protect the rewards.

## [Medium] Creator can change buy/sell royalty up to 50% at any time via updateCred, front-running holders

File: Cred.sol
Function: updateCred()

`updateCred` lets the creator set `buyShareRoyalty` and `sellShareRoyalty` to any value up to `MAX_ROYALTY_RANGE` (5000 = 50%). The royalty values are passed as plain call arguments, not in the signed data. There is no timelock or delay, and trades take effect immediately. Slippage protection is optional: `priceLimit == 0` disables it, and the `createCred` first buy passes 0. The curve then charges the new creator fee in `getPriceData`, and `price - protocolFee - creatorFee` is paid to the seller.

Attack path: 1. Holders hold a cred or are about to sell. 2. The creator, watching the mempool, calls `updateCred` with `sellShareRoyalty = 5000`. 3. Holder sells with `minPrice_ = 0` execute and half of the proceeds go to the creator through `PhiRewards.deposit`. The same works for `buyShareRoyalty` against buyers with `maxPrice_ = 0`.

Impact: Up to half of every trade's value can be extracted from traders who have no limit set, immediately and with no warning.

## [Medium] PhiNFT1155 caches protocolFeeDestination at init, so art-creation fees go to a stale address

File: PhiNFT1155.sol
Function: createArtFromFactory() / initialize()

PhiNFT1155.initialize copies phiFactoryContract.protocolFeeDestination() into its own storage variable protocolFeeDestination (and also uses it as the default royalty recipient via initializeRoyalties). PhiFactory.setProtocolFeeDestination only updates the factory's variable and never pushes the change to the existing per-cred NFT clones. createArtFromFactory then pays artFee to the clone's cached address. Every cred NFT contract created before the change keeps paying the old destination. The same stale value is the default ERC2981 royalty recipient returned by getRoyalties.

Attack path: 1. Owner calls setProtocolFeeDestination(newAddr), for example after a key rotation or compromise of the old address. 2. Artists create further arts on existing cred contracts (the _useExistingNFTContract path). 3. Each createArtFromFactory sends artCreateFee to the old address. 4. The clone's default royalty recipient also stays the old address. The owner has no function to update the clones.

Impact: Protocol fee revenue is misdirected to a retired or compromised address, with no way to repair it for already deployed clones. Default royalties for all existing arts also go to the old address.

## [Medium] createCred/updateCred signatures are replayable and not bound to chain or contract; royalties and creator_ are unsigned

File: Cred.sol
Function: createCred()

The signed data is `(expiresIn, sender, uint256 unused, bondingCurve, credURL, credType, verificationType, merkleRoot)`. Nothing records a used signature or nonce, and the third field is ignored. The hash contains no chainId and no contract address. `creator_`, `buyShareRoyalty_` and `sellShareRoyalty_` are call arguments outside the signed payload. Until it expires, the same signature can be used repeatedly by `sender` to create many creds, and it can also be replayed on another chain or deployment that shares the signer. `creator_` can be set to any address, so the creator or royalty recipient of a signer-approved cred is chosen by the caller.

Attack path: 1. Obtain one valid signature for `sender`. 2. Call `createCred` several times before expiry with the identical `signedData_` and `signature_`, and a different `creator_`, to produce duplicate creds. 3. Set `creator_` to a victim or a controlled address.

Impact: The signer's one-cred-per-signature approval is bypassed. Duplicate or spoof creds can be created, and the cred creator can be attributed to an arbitrary address. In `PhiFactory`, the creator is used as the verifier for merkle claims.

## [Medium] Refund to msg.sender happens before lastTradeTimestamp is set, enabling lock bypass by reentrancy

File: Cred.sol
Function: _handleTrade()

In the buy branch, shares are credited and supply increased. Then excess ETH is refunded with `_msgSender().safeTransferETH(excessPayment)`, and only afterwards is `lastTradeTimestamp[credId_][curator_]` updated. `_handleTrade` has no `nonReentrant`; only the batch path uses `locked`. In the refund callback, the lock still shows the old value (0 for a fresh buyer), so the attacker can call `sellShareCred` on the freshly bought shares.

Attack path: 1. Attacker contract calls `buyShareCred` with msg.value above the price. 2. In `receive()` during the refund, it calls `sellShareCred` for the same cred. 3. The check `block.timestamp <= last + 10 minutes` passes because the timestamp is not yet written, so the buy and sell happen in one transaction. 4. After the callback, `lastTradeTimestamp` is set, but the position is already sold.

Impact: The 10-minute `SHARE_LOCK_PERIOD` anti-flash-trade protection is defeated. Atomic buy and sell around other actions (curator reward snapshots, `distribute`) costs only fees.

## [Medium] imageURI is unsigned and overwrites the minter's stored URI, so third parties can set it

File: PhiNFT1155.sol
Function: mint() / claimFromFactory()

`mint` does `advancedTokenURI[tokenId_][to_] = imageURI_` unconditionally. `imageURI_` comes from caller-supplied `MintArgs` and is not covered by the signature or Merkle leaf. The caller is not tied to the `minter_`. Anyone holding a valid proof or signature for a victim can submit a claim with an arbitrary `imageURI`, which overwrites the victim's per-minter URI.

Attack path: 1. A victim minter has a Merkle proof or signature that is public. 2. A third party calls merkleClaim/signatureClaim for that minter with a malicious `imageURI` and pays the fee. 3. The victim's `uri(tokenId, minter)` now returns the attacker's chosen URI.

Impact: Metadata or image of a minter's token can be replaced by a third party. Phishing or misleading content is possible.

## [Medium] Unbounded curator list (zero-balance entries never removed) can make distribute() run out of gas

File: CuratorRewardsDistributor.sol
Function: distribute()

distribute() calls credContract.getCuratorAddresses(credId,0,0), which iterates the whole EnumerableMap shareBalance[credId]. It then loops again, making an external getShareNumber() call per holder, twice. In Cred._updateCuratorShareBalance a full sell only does shareBalance.set(sender, 0). The key is never removed, so the map length only grows. buyShareCredFor lets anyone create entries for arbitrary addresses. A single curator address cannot be removed from the list.

Attack path: 1) Attacker uses many fresh addresses. Each buys 1 share, up to 999 at once because of MAX_SUPPLY. 2) After 10 minutes each sells its share. The entry stays in the map with value 0. 3) Repeat with new addresses until the map is too large to iterate within the block gas limit. 4) distribute(credId) and getCuratorAddresses then revert for out-of-gas.

Impact: The ETH in CuratorRewardsDistributor.balanceOf[credId] is permanently locked, and all future curate rewards for that cred accumulate with no way out. The attacker only pays the round-trip trading fees.

## [Medium] TxOriginMismatch anti-contract check is bypassed by routing through claim()/batchClaim()

File: PhiFactory.sol
Function: _validateAndUpdateClaimState() / claim() / batchClaim()

_validateAndUpdateClaimState reverts when tx.origin != msg.sender, unless msg.sender is the art contract or the factory itself (msg.sender == address(this)). claim() and batchClaim() reach signatureClaim and merkleClaim through this.signatureClaim and this.merkleClaim, so msg.sender is always the factory and the check always passes. Any smart contract, relayer or bot can therefore claim through claim() regardless of tx.origin. The effective rule is only 'do not call signatureClaim or merkleClaim directly from a contract'. The check does not enforce what it appears to enforce.

Attack path: 1. A contract that is not tx.origin calls PhiFactory.claim(encodedData) or batchClaim with a valid signature or Merkle proof for any minter. 2. The inner this.merkleClaim or this.signatureClaim call has msg.sender == factory, so the origin check is skipped. 3. The claim is processed for any minter_ named in the data.

Impact: The origin restriction on claims is ineffective. Third parties and contracts can mint to arbitrary minters, and combined with the unsigned quantity/imageURI problem the mint parameters are attacker-controlled.

## [Medium] Fee setters treat mintProtocolFee and artCreateFee as basis points but they are used as flat wei amounts

File: PhiFactory.sol
Function: setProtocolFee() / setArtCreatFee() / getArtMintFee() / _processClaim()

setProtocolFee and setArtCreatFee cap values at 10_000 and document them as basis points. The values are used as absolute wei: getArtMintFee adds quantity_ * mintProtocolFee, _processClaim sends mintProtocolFee * quantity_ to protocolFeeDestination, and createArtFromFactory sends artCreateFee as ETH. After the first call to either setter the owner can never configure more than 10_000 wei (about 1e-14 ETH) per mint or art creation. Only the unchecked initialize value can be larger. The cap makes the protocol fees effectively zero and cannot be raised later.

Attack path: 1. Owner tries to set a meaningful fee, for example 0.0001 ETH, via setProtocolFee or setArtCreatFee. 2. The call reverts with ProtocolFeeTooHigh or ArtCreatFeeTooHigh. 3. The owner can only choose a value of at most 10_000 wei, which loses the initial fee.

Impact: Protocol revenue from mint and creation fees cannot be set to a meaningful level after deployment, and an owner who adjusts either fee permanently drops it to a negligible amount.

## [Medium] createCred increments credIdCounter after external refund call; reentrancy corrupts cred IDs

File: Cred.sol
Function: _createCredInternal()

`_createCredInternal` writes `creds[credIdCounter]` and calls `buyShareCred(credIdCounter, 1, 0)`. That call refunds excess ETH to `msg.sender` inside `_handleTrade`. `credIdCounter += 1` runs only afterwards, and there is no reentrancy guard. A contract caller can re-enter `createCred` from the refund callback, for example by replaying the same signature. The nested call overwrites `creds[N]` and increments the counter. The outer call then increments it again and returns `credIdCounter - 1`, which is a non-existent id N+1. The outer call then writes `credsMerkeRoot` to that skipped id.

Attack path: 1. A contract calls `createCred` with excess msg.value. 2. In `receive()`, it calls `createCred` again with the same or another valid signature. 3. Id N is overwritten and id N+1 is skipped. 4. A stale `credsMerkeRoot[N+1]` is left behind for the next cred to be created at N+1.

Impact: Cred state is overwritten and ids are skipped. A stale merkle root can be inherited by an unrelated future cred.

## [Medium] Zero-balance holders are never removed from shareBalance map, so holder enumeration can be bloated to DoS distribute()

File: Cred.sol
Function: _updateCuratorShareBalance()

On sells, `shareBalance[credId_].set(sender_, 0)` is called, so the address stays in the EnumerableMap forever. Only the per-address cred list is cleaned up. The map length therefore only grows. `_getCuratorData` iterates all entries, including zero ones. `CuratorRewardsDistributor.distribute` calls `getCuratorAddresses(credId, 0, 0)` and then loops with an external `getShareNumber` call per holder. An attacker can inflate the entry count cheaply, using `buyShareCredFor` or by cycling buy and sell from fresh addresses.

Attack path: 1. The attacker uses many fresh addresses, each buying 1 share and selling it after the lock period (paying only the fees). 2. The map for the cred grows to thousands of entries. 3. `distribute(credId)` and the `getCuratorAddresses` views run out of gas, and curator rewards for that cred get stuck in `CuratorRewardsDistributor.balanceOf`.

Impact: Curator reward distribution for a cred can be blocked, which locks the accumulated rewards.

## [Medium] Claim signature's chainId field is not validated against block.chainid in signatureClaim

File: PhiFactory.sol
Function: signatureClaim()

`signatureClaim` decodes the chain-id slot of `encodeData_` as an unnamed value and never compares it to `block.chainid`. It also does not compare `verifier_` or any other field to the caller. `claim()` builds the data with `block.chainid`, but direct callers supply `encodeData_` themselves. Replay protection across deployments depends only on a field that is never compared.

Attack path: 1. The same signer runs the factory on multiple chains. 2. A claim signed for chain A with artId N is submitted on chain B, where artId N also exists. 3. It passes the signature check.

Impact: Cross-chain claim replay when signer keys and art IDs overlap.

## [Medium] Royalty BPS is unbounded and royalties cannot be disabled

File: CreatorRoyaltiesControl.sol
Function: _updateRoyalties() / royaltyInfo()

`_updateRoyalties` accepts any `royaltyBPS` as long as the recipient is non-zero when BPS > 0. Nothing caps it at 10_000. `royaltyInfo` returns `royaltyBPS * salePrice / 10000`, which can exceed the sale price. Setting the recipient to the zero address with BPS 0 makes `getRoyalties` fall back to the default 500 BPS to the protocol recipient. An artist cannot set zero royalties.

Attack path: 1. The artist calls `updateArtSettings` with `royaltyBPS` above 10000. 2. Marketplaces calling `royaltyInfo` get a royalty larger than the price. 3. Sales revert or are over-charged.

Impact: Marketplaces can be broken for that token, and an artist cannot opt out of the default royalty.

## [Medium] buyShareCredFor lets anyone reset a victim's lastTradeTimestamp and keep their shares locked

File: Cred.sol
Function: _handleTrade()

buyShareCredFor(credId, amount, curator_, maxPrice) accepts any curator_. _handleTrade then sets lastTradeTimestamp[credId_][curator_] = block.timestamp for the victim. A sell requires block.timestamp > lastTradeTimestamp + 10 minutes, so each gifted share restarts the victim's lock. The same applies to batchBuyShareCred with a chosen curator_. The victim has no way to opt out.

Attack path: The attacker repeatedly calls buyShareCredFor(credId, 1, victim, 0) at intervals shorter than 10 minutes. The victim's sellShareCred reverts with ShareLockPeriodNotPassed for as long as the attacker keeps doing this.

Impact: The victim cannot exit their position, for example during a price drop. The attacker pays gas and a small fee, and the gifted shares are not lost to the attacker in value terms.

## [Medium] createArt never enforces artCreateFee on msg.value and the overpayment refund is sent to the factory, which cannot receive ETH

File: PhiFactory.sol
Function: createArt() / _useExistingNFTContract() / createArtFromFactory()

createArt is payable but never checks msg.value >= artCreateFee. It forwards msg.value to PhiNFT1155.createArtFromFactory, which pays artFee to the fee destination from its own balance. It then refunds msg.value - artFee to _msgSender(), which is the factory. PhiFactory has no receive() or fallback, so any overpayment makes the refund revert and createArt fails with CreateFailed. In the other direction, for an already deployed cred NFT contract (which has a payable receive()), an underpaying caller is covered by ETH already sitting in that contract, for example refunds that got stuck there through Claimable. Stuck ETH is thus consumed as protocol fee, and users must send the exact fee.

Attack path: 1. A creator sends more than artCreateFee, or the fee changes before the transaction lands, and createArt reverts. 2. Alternatively, a creator creates a second art on an existing cred contract with msg.value = 0. 3. The NFT contract pays artFee out of its own accumulated ETH.

Impact: Overpaying users cannot create arts (DoS or wasted gas). Underpaying creators avoid the fee, and ETH held by NFT contracts is drained to the protocol destination.
